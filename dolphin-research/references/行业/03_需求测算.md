# 第3章 需求测算

> **本章目的**：从需求锚、驱动因子到量化测算和结构拆分，把“需求有多大、是否可持续、结构如何变”算清楚。

**本章小节**：3.1 下游资本开支锚与需求可持续性｜3.2 需求驱动拆解与底层公式｜3.3 需求链式测算、口径与三角验证｜3.4 需求结构拆分与迁移｜3.5 需求弹性、透支与季节波动

## 3.1 下游资本开支锚与需求可持续性

> 本节导读：本节解决“上游的需求到底来自谁、这笔钱能花多久”的问题：把下游客户（云厂、晶圆厂、模型厂）的Capex当作需求锚，并检验这个锚是否可持续。研究AI芯片、服务器、光模块、存储、电力以及半导体设备等任何“卖铲子”的公司时，每次财报先用本节方法更新需求底座，再判断上调是真需求还是涨价、Capex占收入是否触顶、模型厂收入能否继续托住基建。供给方自身的扩产Capex见 4.1，订单→GW→Capex的链式推算见 3.3，需求结构的拆分见 3.4。

### 3.1.1 大客户Capex的汇总预测、节奏判断与滚动更新

**方法要点**：把公司最大客户（四大云厂商Meta、谷歌、微软、亚马逊，后扩到加上甲骨文的五大CSP）的资本开支指引和管理层交流加总，给出年度总Capex和同比增速，作为AI硬件/芯片需求的“基本盘”“β”和需求底座，每次大厂财报后滚动更新，并判断年内投入节奏。

**操作步骤 / 拆分口径**

1. 每篇AI硬件、芯片财报都更新一次“四大核心云厂商合计Capex预测及同比”：逐家记录最新指引区间、同比增速和相对市场预期的差（好于、符合或低于预期）。
2. 汇总口径随客户范围扩展：先是谷歌、Meta、微软、亚马逊四家，后扩到五大CSP（加甲骨文），并同步把预测年份向后推一年（如2027年）。
3. 滚动更新：随各家财报陆续发布，记录合计预测的“旧值→新值”，如6000亿→6600亿→7000亿以上→8000亿以上（五大）；2027年预期则从市场1.1-1.2万亿美元被提到1.3万亿美元。
4. 判断年内节奏：新品（Rubin、MI400）通常下半年量产，投入呈“前低后高”，用它解释公司收入的季度节奏。
5. 把大厂Capex与公司自身份额挂钩：Capex里AI芯片的占比和公司份额需要另行估算（见 3.3 的链式测算），本步只给“基本盘”。
6. 当大厂上调Capex而上游股价不涨时，不要机械地当作利好，转去判断市场关注点是否已切换到竞争和毛利率（见 3.1.3）。

**关键指标与数据来源**：各云厂商Capex指引与同比、合计Capex预测、上下半年节奏、是否上调、单家上调幅度。数据来自云厂商财报、电话会和管理层交流，以及产业链上游公司在财报中转述的客户预期。

**判断标准**

- 合计Capex逐季上修、同比增速上台阶（约50%→60%以上→接近80%），说明需求底座在加固；多数大厂仍在上调，说明AI Capex叙事没被打破。
- 单家上调的“幅度与预期差”比绝对值更重要：好于预期是正向信号，只是符合预期则需要进一步归因（见 3.1.2）。
- 推理链条：大厂Capex（总盘）→乘以AI芯片占比和公司份额→公司下一财年业绩的可见度。英伟达就把Capex上修视作“为公司2027财年的业绩高增长带来了保障”。
- 节奏判断：前低后高与新品量产周期吻合，则上半年收入偏弱不代表需求弱。

**海豚案例**

- AMD（2026-02-04）：Meta 2026年Capex 1150~1350亿美元（+60%~87%），好于预期的1100亿；四大合计超6000亿，同比约50%，节奏前低后高，与Rubin、MI400的量产周期匹配，用于解释公司收入的季度节奏。
- 戴尔（2026-02-27）：四大合计6600亿，同比+62%。
- 博通（2026-03-05）：四大合计6600亿，同比+60%以上。
- Marvell（2026-03-06）：亚马逊2026年Capex 2000亿，+50%。
- 英伟达（2026-02-26）：四大云厂商2026年资本开支有望达6600亿美元以上、同比+62%；英伟达（2026-05-21）：上修到7000亿以上、同比接近80%，并称“为公司2027财年的业绩高增长带来了保障”。
- 戴尔（2026-05-29）：四大合计7000亿以上，同比约+80%。
- AMD《CPU“狂飙”》（2026-05-06）：Meta、微软上调Capex，预计四大云厂商2026年合计Capex超过7000亿美元，同比+70%以上，节奏前低后高。
- AMD《AMD：狂抢“AI大单”》（2026-08-05）：谷歌、Meta、亚马逊再次上调，预计五大（加甲骨文）合计超过8000亿，同比+80%以上。
- 海力士（2026-07-29）：市场对2026年五大CSP资本开支的预期已超过8000亿美元，同比+82%。
- 戴尔（2026-09-02）：英伟达把五大CSP 2027年Capex预期提到1.3万亿美元（原市场1.1-1.2万亿）。

**适用场景与注意事项**：适合AI芯片、服务器、光模块、新云、电力设备等AI基础设施链的B2B上游供应商，需要每季跟踪各家财报。局限：Capex总盘不等于公司可得订单，里面AI芯片占比、公司份额必须另行估算；合计预测随财报不断变动，引用时要注明口径（四大还是五大、哪一天的预测）。

### 3.1.2 区分Capex上调来自涨价还是真实需求，并观察大厂态度变化

**方法要点**：Capex上调不都是强信号。如果上调主要来自存储、零部件涨价，而不是AI需求真的提升，就不能当作需求强化；同时要观察大厂态度的分化，有人不再上调且被市场奖励，可能引发连锁的谨慎投入。

**操作步骤 / 拆分口径**

1. 先把五大CSP的资本开支预期加总并算增速，作为AI链的最终需求。
2. 每次单家上调时，量出上调幅度（旧区间→新区间），并与市场预期对比。
3. 归因：上调有多少来自存储、零部件涨价，有多少来自算力扩容等真实需求。主要来自涨价的，不算强信号。
4. 观察大厂态度：是否有大厂不再上调、股价反而被奖励；若有，判断是否会形成“多米诺骨牌”式的连锁谨慎。
5. 与有明确增量需求信号的上调（如多家同时上调、需求确定性强）做对比。

**关键指标与数据来源**：五大CSP资本开支预期及同比、单家资本开支上调幅度、上调原因、上调是否符合预期、市场对股价的反应。

**判断标准**

- 上调幅度小（如约100亿）且只是符合预期，同时存储涨价明显，则市场归因于涨价，信号偏弱。
- 多家大厂（谷歌、Meta）同时上调全年Capex，需求确定性较强。
- 有大厂不再上调却被市场奖励，意味着市场对“少花钱”有偏好，其他大厂可能效仿，是对上游的潜在风险。

**海豚案例**

- 海力士（2026-07-29）：市场对2026年五大CSP资本开支预期已超8000亿美元，同比+82%；谷歌把全年资本开支从1800-1900亿提到1950-2050亿，增幅约100亿，只是符合预期，市场更多归因于存储涨价，不算强信号。
- ARM（2026-07-30）：微软不再上调资本开支并获市场奖励，可能形成多米诺骨牌效应。
- 博通（2026-09-03）：谷歌和Meta上调全年资本开支，需求确定性较强。

**适用场景与注意事项**：适用于AI算力链的所有环节，尤其是存储、零部件价格正在上涨的阶段。易错点：涨价带来的名义Capex上升会虚增“需求”，应与出货量、GW、卡数等实物量交叉验证（见 3.3）。

### 3.1.3 Capex指引对照一致预期与资金预期，读出产业链叙事与叙事切换

**方法要点**：不只看大厂Capex“多少”，更要看它与产业链资金预期、次年一致预期之间的差，以及管理层的定性表述。同一份指引可以因预期差而成为“算力过剩、产业链见顶”叙事的导火索；叙事也会从“Capex等于增长信号”切换到“Capex必须有变现和现金流背书”。

**操作步骤 / 拆分口径**

1. 记录大客户本年Capex指引的变化方式：是上调区间上限、下限，还是整体上移。
2. 与产业链资金的预期对比：次年Capex的一致预期，以及激进资金的极端假设（如直接按翻倍算）。
3. 记录管理层的定性表述（例如算力供不应求、先做两年扩产计划）。
4. 记录有没有给次年的定量指引，以及没给的含义（次年指引通常在下半年或Q4给出，缺失本身不代表看空，但在高预期下会放大失望）。
5. 判断对上游算力、存储产业链的情绪冲击，并用它解释股价的β层面波动和大厂财报后的分化。
6. 跟踪叙事切换：从“Capex等于增长信号，越多越好”到“Capex必须有加速的变现和健康的现金流背书”。当大厂上调Capex而上游股价不涨，就是关注点已转向竞争和毛利率的信号。

**关键指标与数据来源**：Capex指引；次年Capex一致预期；管理层定性表述；是否给出次年定量指引；上调Capex后上游股价反应。

**判断标准**

- 只上调区间下限、未达资金心理预期，加上未给次年定量指引，会被解读成“算力过剩”的导火索。
- 上调Capex但上游股价不涨，说明市场定价重点已转向竞争和毛利率，而不是总量。
- 多数大厂仍在上调、AI Capex叙事没被打破时，股价回调更多是Capex可持续性的β影响，应在大厂之间分化看待（亚马逊和微软更优质）。

**海豚案例**

- Meta（2026-07-30）：2026年Capex只上调了区间下限，未达产业链资金的心理预期；财报前市场对2027年Capex的预期为2250-2500亿，激进资金按翻倍给；管理层未给27年定量指引（通常在下半年或Q4给出），Meta成为“算力过剩、产业链见顶”叙事的导火索。
- AMD《CPU“狂飙”》（2026-05-06）：用四大云厂商合计Capex作为AI芯片市场的β，并提示市场叙事从“Capex等于增长信号”切换为“Capex需要有加速的变现和健康的现金流背书”。
- AMD《AMD：狂抢“AI大单”》（2026-08-05）：股价前期回调主要受Capex可持续性的β影响，市场关注点已切换；亚马逊和微软更优质；多数大厂仍在上调，AI Capex叙事没被打破。
- 滚动汇总客户Capex时的通用判断（英伟达、戴尔等滚动更新案例见 3.1.1）：如果大厂上调Capex而上游股价不涨，说明市场关注点已转向竞争和毛利率。

**适用场景与注意事项**：研究AI基础设施产业链时，用下游巨头的Capex作领先指标和情绪指标。注意区分“绝对量没问题但低于预期”与“真正的需求转弱”，前者造成估值波动，后者才改变基本面。

### 3.1.4 下游Capex推上游需求：晶圆厂Capex看设备商，云厂Capex看AI芯片

**方法要点**：沿产业链用“客户的Capex”预判“供应商的收入”：晶圆厂Capex是设备商业绩的前瞻指标，云厂Capex是AI芯片的需求来源；并把设备商的指引上调归因到具体客户群。

**操作步骤 / 拆分口径**

1. 汇总核心晶圆厂（台积电、三星、英特尔、美光、海力士）的资本开支指引，追踪每次上调（旧值→新值）。
2. 分逻辑类和存储类估算增速，并估算全球核心晶圆厂Capex总增速。
3. 对照市场预期：指引是否高于预期（如520-560亿 vs 预期480-500亿）。
4. 把设备商的指引上调归因到具体客户群（如判断为存储厂追加订单），再据此判断设备商下季、全年预期的抬升幅度。
5. 同样的逻辑用于AI链：云厂商Capex→AI芯片；晶圆厂Capex→设备商。

**关键指标与数据来源**：各晶圆厂Capex指引及上调幅度、逻辑与存储Capex增速、全球核心晶圆厂Capex增速、设备商指引区间与机构预期。

**判断标准**

- 晶圆厂Capex指引高于预期，既反映需求信心，也反映先进制程（如2nm）扩产节奏，对设备商是直接利好。
- 设备商指引大幅上调，要看是哪类客户驱动：存储厂追加订单与逻辑厂扩产的持续性和价格含义不同。
- 推理链条：下游上调Capex→机构把设备商预期调高→设备商财报兑现。

**海豚案例**

- 台积电（2026-01-15）：2025年Capex 409亿美元（+110亿），2026年指引520-560亿 vs 预期480-500亿，反映对需求和2nm扩产的信心。
- ASML（2026-01-28）：台积电上调Capex后，机构把ASML下季预期提高到约85亿、全年增速提到20%以上。
- AMAT（2026-02-13）：台积电520-560亿，美光200亿，三星加大存储投入，2026年全球核心晶圆厂资本开支增速20%以上；台积电、美光提升Capex直接带动公司业绩。
- ASML（2026-07-15）：海豚君预估2026年逻辑类厂商资本开支增速20%以上，存储类40%；美光全年资本开支从250亿上调到270亿；台积电指引540-560亿，市场预期已超560亿；ASML全年指引从360-400亿提到430-450亿，归因于存储厂追加订单。

**适用场景与注意事项**：适用于半导体设备和材料公司，也适用于其他“客户Capex驱动”的供应商。注意设备订单与确认收入之间存在时滞，指引上调不等于当季收入兑现。

### 3.1.5 Capex/收入比与短周期资产占比：持续性天花板与估值阶段

**方法要点**：把云厂商Capex占收入的比重与历史区间比较，判断Capex高增长还能不能持续；再看Capex中GPU等短周期资产的占比，评估投入的质量；据此判断上游AI链公司处在“高增长、拔估值”阶段，还是“业绩增长、消化估值”阶段。

**操作步骤 / 拆分口径**

1. 计算云厂商Capex/收入，与其历史区间对比。
2. 对比收入增速：如果Capex/收入已远高于历史、而收入增速有限，Capex的高增长难以持续。
3. 推断未来某一年的Capex增速会大幅回落，并给出大致年份。
4. 拆Capex结构，关注GPU等短周期资产占比及其环比变化。
5. 把结论映射到上游估值阶段：高增长、拔估值 → 业绩增长、消化估值（估值回落到30倍以下）。
6. 最好结合云厂商的现金流和AI回报（ROI）一起看。

**关键指标与数据来源**：Capex/收入（历史区间vs当前）、云厂商收入增速、Capex增速、Capex中短周期资产占比。

**判断标准**

- Capex/收入已达5~6成后，再提升的空间不大，市场据此预期大厂Capex增速在2027年左右大幅回落。
- 短周期资产（GPU）占比越高，投入越像“消耗品”，折旧压力越快显现；占比提升说明当期投入偏向算力而非长周期基建。
- 推理链条：Capex/收入触顶→Capex增速回落→上游收入增速回落→估值从“拔”转向“消化”。

**海豚案例**

- 博通（2026-03-05）：Meta 2026年Capex 1150~1350亿，超过收入的50%，远高于此前20~25%的区间；谷歌、微软的Capex占比也将升到4成以上。Meta收入增速约15~20%，Capex/收入到5~6成后再提升的空间不大，所以市场预期大厂Capex增速在2027年左右大幅回落，“高增长、拔估值”阶段结束；博通进入“业绩增长、消化估值”阶段，估值回落到30倍以下。同时指出Meta 2026年Capex已占收入一半以上，继续提升空间有限，市场担心持续性。
- 微软（2026-01-29）：Capex中约2/3（约250亿）用于GPU等短周期资产（上季为1/2）。

**适用场景与注意事项**：适合判断上游AI硬件链的估值周期。局限：Capex/收入比是“天花板”的粗尺，不是精确拐点；需配合云厂商的自由现金流与AI变现（见 3.1.7）一起判断。

### 3.1.6 中美Capex增速与Capex/收入比对比，结合折旧周期判断AI投资回报压力

**方法要点**：对比中国大厂与北美科技巨头的资本开支增速、Capex/收入和折旧周期，判断AI投入对利润和现金流的压力，进而推断大厂在应用落地上的施展空间。

**操作步骤 / 拆分口径**

1. 汇总中国四家（字节、腾讯、阿里、百度）的整体资本开支及增速，结合调研数据和市场预期推下一年增速。
2. 计算各自Capex/收入，与北美科技巨头对比。
3. 对比竞争路线：中国卷应用落地，北美卷高端模型。
4. 对比环境优势：电力、数据中心基建折旧等后续运行成本。
5. 统一折旧周期（4-5年）后判断投资回报，是否需要担心现金流、利润崩塌。

**关键指标与数据来源**：资本开支增速、资本开支/收入、折旧年限；各公司资本开支披露和市场预期，加上调研数据。

**判断标准**

- 中国四家2025年整体资本开支增长45%，2026年预计再增长约30%；Capex占收入的比重大多在10%左右，明显低于北美科技巨头动辄20%以上的投入强度。
- 同样4-5年的折旧周期下，尽管中国终端消费力不足，大厂的AI投资回报或许也不至于太差，还没到需要担心现金流、利润崩塌的程度，这给了它们在应用落地上更多施展空间。

**海豚案例**

- 中国AI互联网《火拼 AI 互联网…》（2026-01-09）：字节、腾讯、阿里、百度2025年Capex合计+45%、2026年预计约+30%；Capex/收入约10% vs 北美20%以上；4-5年折旧周期下AI投资回报压力可控。

**适用场景与注意事项**：适用于判断AI投入对利润和现金流的压力。需要各公司的资本开支披露和市场预期。注意中美口径差异（折旧年限、租赁与自建比例）会影响比较结果。

### 3.1.7 用AI模型厂ARR斜率与合计ARR加速度检验Capex可持续性

**方法要点**：AI产业链像一个倒金字塔，OpenAI与Anthropic等模型厂的收入是基建逐级加杠杆（云厂Capex→GPU、存储、光模块）的底层根基。用第三方高频数据跟踪模型厂ARR的斜率和加速度，作为下游AI商业化和经济性的前瞻指标，检验Capex的可持续性。

**操作步骤 / 拆分口径**

变体A：ARR斜率跟踪（Ticker Trends等）

1. 用Ticker Trends等第三方数据跟踪闭源模型厂（Anthropic、OpenAI）的ARR及增长斜率。
2. 判断：ARR加速支撑CSP继续上调Capex；斜率放缓引发Capex回落的担忧。
3. 用它解释AI链板块的回调（中国开源模型、Anthropic ARR斜率等事件）。

变体B：斜率放缓的传导链

1. 斜率放缓→Token价格下降→模型经济性变差。
2. →大厂资本开支更谨慎→AI实验室订单不确定。
3. →影响存储、ASIC、代工的估值。

变体C：合计ARR加速度与预期差（短评思路）

1. 出现新数据（如Anthropic 7月底年化收入650亿美元）时，不看绝对值。
2. ①与第三方高频数据（Yipit Data、Tickertrends）此前估算对比，更低就是预期差。
3. ②看两家合计收入的加速度（二阶导）是否放缓：OpenAI在Codex降价后或有边际加速，但合计可能放缓。
4. ③追问原因：模型降价打价格战压低了ARR增长，还是模型迭代没有进一步激发Token用量。
5. 据此解释存储、光模块等上游的暴跌。

**关键指标与数据来源**：Anthropic/OpenAI ARR及增速斜率、合计ARR加速度、第三方估算值（Ticker Trends、Yipit Data）、Token用量。

**判断标准**

- 斜率放缓但绝对值仍增长：放大对模型经济性的担忧，存储、ASIC、光模块、代工估值承压。
- 新数据低于第三方估算：形成预期差，对依赖该需求的上游短期冲击大。
- 合计ARR二阶导转负：说明“价格战压低收入”或“Token用量未被激发”，需要追问原因再下结论。
- 个别客户的展望被ARR斜率“打折”：如把需求拆到具体合同时，ARR放缓会使该部分展望折价。

**海豚案例**

- 英伟达（2026-08-27）：此前AI行业回调主要受中国开源模型和Anthropic ARR斜率等事件影响；Ticker Trends显示Anthropic斜率趋缓、OpenAI仍在加速，两家的ARR是市场跟踪闭源模型的主要对象。

- 台积电（2026-10-15）：Anthropic ARR时不时掉链子，AI融资成本走高，AI链整体承压。
- SK海力士/Coherent/Lumentum《(短评)一个数字引发的暴跌》（2026-08-19）：Anthropic 7月底年化收入650亿美元，与Yipit Data、Tickertrends此前估算比较，并追问两家合计收入加速度是否放缓，以此解释存储、光模块暴跌。

**适用场景与注意事项**：适用于AI产业链上游（芯片、服务器、光模块、存储、电力）对需求信号的敏感度分析。局限：第三方ARR数据有估算误差；单个数据点需要交叉验证；ARR只是上游需求的“根基”，不能直接换算为GW或Capex（见 3.3 的链式测算）。

## 3.2 需求驱动拆解与底层公式

> 本节导读：本节解决“需求是被什么因子驱动的、底层物理或经济公式长什么样”的问题，是做定量测算之前的“选变量”步骤。遇到新技术、新产品形态或新政策时，先用本节方法找出新增使用场景、写出驱动公式、识别需求乘数和反向抵消项（软件效率），再进入 3.3 做链式测算。AI推理侧的内存、存储、CPU需求拆解与储能的政策经济性拆解都放在这里；结构占比的拆分见 3.4，完整的量化测算链见 3.3。

### 3.2.1 推理存储需求驱动公式「AI用户数×使用频次×上下文长度」与「Token电池」价值折算

**方法要点**：先区分训练时代与推理时代存储扮演的角色，指出推理期存储需求与用户数、使用频次、上下文长度强绑定；再把存储价值折算为“被节省的算力与电费”，把NAND从成本项重新定价为算力节省项。

**操作步骤 / 拆分口径**

1. 训练期：NAND只是外围“数据仓库”，存语料、权重、Checkpoint等静态数据，可替代性强（丢了从数据湖重下即可，只花带宽和少量电费）。
2. 推理期：计算变成高并发、持续性的“动态消耗”，存储需求与「AI用户数×使用频次×上下文长度」强绑定。
3. 关键质变：NAND首次存储“计算的中间产物”（KV Cache），丢失后无备份，只能用GPU重算，因此存储价值第一次可以直接折算为“被节省的算力与电费”。
4. 借用公司说法把SSD定义为“Token电池”：Token是已经做过的功，存起来比重算更划算。
5. 据此论证需求刚性和价格脱敏：存储不再只是成本项，而是算力节省项。

**关键指标与数据来源**：AI用户数、使用频次、上下文长度、KV Cache规模、重算成本（GPU时间与电费）。

**判断标准**

- 存储的价值判断标准从“每GB多少钱”变为“比重算省多少算力和电费”。只要存比重算划算，需求就具有刚性。
- 推理链条：训练→推理→动态消耗→KV Cache（中间产物，丢失需重算）→存储价值可折算为算力节省→需求刚性、价格敏感度下降。

**海豚案例**

- NAND《从绿叶到鲜花，AI 推理如何为 NAND「逆天改命」？》（2026-09-30）：训练 vs 推理两阶段对比；引用闪迪“SSD本质上已经进化为一块Token电池”。

**适用场景与注意事项**：适用于AI基础设施中任何“以存代算”环节（DRAM、CXL内存、NAND、网络存储）的需求论证。注意算法压缩（如KV压缩）对单位需求的抵消（见 3.2.4、3.2.7）。

### 3.2.2 内存容量需求二分：底仓（参数）+ 弹性（KV缓存）× 会话数

**方法要点**：把AI存力需求先拆成“容量”和“速度”两维，容量再拆成线性可预测的“底仓”和非线性的“弹性”，由此指出真正会爆的是KV缓存，而不是模型参数。

**操作步骤 / 拆分口径**

1. 存力需求先分容量与速度两维。
2. 容量需求再拆：
   - 底仓 = 模型参数量 × 每参数字节数，线性可预测。
   - 弹性 = 推理KV缓存，取决于上下文长度和注意力架构的压缩效率，非线性。
3. 总量 = 单会话缓存 × 并发会话数；用户与会话爆发时，总需求可达数十乃至上百倍。
4. 结论：用的人越多，比模型越大更能撑起内存需求。

**关键指标与数据来源**：参数量、每参数字节、单实例参数存储GB、上下文长度、单会话KV缓存、并发会话数。需要模型架构参数（层数、头数、量化精度）。

**判断标准**

- 底仓：Qwen初代720亿参数→Qwen3.8 Max约2.4万亿，单实例存参数从135GB涨到约2300GB（约17倍）。
- 弹性：Qwen3.8 Max上下文是Qwen2.5的8倍，单会话缓存只多约12%，说明软件进步压住了单会话需求。
- 总需求的主驱动是会话数（用户数），而不是单模型规模。

**海豚案例**

- 《(短评)内存需求里真正会爆的是KV缓存》（2026-10-07）：上述底仓+弹性拆分，结论“用的人越多”比“模型越大”更能撑起内存需求。

**适用场景与注意事项**：适用于测算AI推理对DRAM/HBM/SSD的需求。易错点：只看参数线性增长会低估总量，只看单会话缓存又会忽视会话数放大。具体的参数内存与KV缓存测算见 3.2.3、3.2.4。

### 3.2.3 模型参数的内存需求测算：总参数量 × 每参数字节（存储精度）

**方法要点**：AI对内存容量的第一块需求是存放全部模型参数，近乎线性可测，用来刻画内存需求的长期驱动。

**操作步骤 / 拆分口径**

1. 公式：所需内存 = 总参数量 × 每参数字节数（BF16为2字节，FP8为1字节或更低）。
2. 取代表性模型系列跨代对比：Qwen从初代720亿参数到Qwen3.8 Max约2.4T参数。
3. 算出每个模型实例存参数所需内存的变化：从135GB增至近2300GB，约17倍。
4. 叠加精度下降的抵消作用（BF16→FP8→FP4）。
5. MoE模型区分总参数（影响容量）和激活参数（影响带宽）。

**关键指标与数据来源**：模型总参数量、存储精度（BF16/FP8/FP4）、单实例参数内存（GB）；来源为模型厂公布的参数规模。

**判断标准**：旗舰模型参数在3-4年间增长几十倍，是内存需求的长期驱动；精度下降只是部分抵消参数增长。

**海豚案例**

- Qwen系列《存力接棒算力，HBM为什么“脱颖而出”？》（2026-09-17）：72B→约2.4T参数，单实例参数内存135GB→近2300GB（约17倍）。

**适用场景与注意事项**：适用于从模型演进推导硬件需求。MoE模型必须区分总参数与激活参数，否则容量与带宽需求会混在一起。

### 3.2.4 KV缓存总量测算：上下文长度 × 注意力压缩效率 × 并发会话数

**方法要点**：KV缓存需求不是线性的，取决于上下文长度和注意力架构对缓存的压缩效率；总需求等于单会话缓存乘以会话数，会话数的爆发才是放大器。

**操作步骤 / 拆分口径**

变体A：按单会话缓存测算（Qwen系列）

1. 假设使用最大上下文的80%，自行测算单会话KV缓存。
2. Qwen3.8 Max最大上下文是Qwen2.5的约8倍，但单会话缓存约36GB，只比Qwen2.5高约12%，是缓存技术进步的结果。
3. 总需求 = 单会话缓存 × 会话数。AI用户数和会话数飞速增长，总缓存需求仍可能增长数十乃至上百倍。
4. 单实例示例：同时处理32个会话时，Qwen3.8 Max单实例总内存 = 参数2.3TB + KV缓存1.3TB = 3.6TB。
5. 补充：Agent执行写文档、操作Excel等传统运算，也会产生内存和闪存需求，但不需要HBM这类高规格产品。

变体B：按乘积公式测算

1. 总量 = 上下文长度 × 并发会话数 × 单Token存储量。
2. 上下文每年翻倍以上（4K→128K→1M+），对总量线性放大。
3. 并发会话数与推理轮次由应用架构放大（见 3.2.5）。
4. 单Token存储量要考虑压缩算法（如KDA、TurboQuant）的下修。

**关键指标与数据来源**：上下文长度、单会话KV缓存（GB）、并发会话数、用户数、单Token KV字节数、上下文增速。

**判断标准**

- 单会话缓存增速远低于上下文增速，说明软件在压制单位需求，但不能据此推断总需求下降。
- 总需求的主要变量是并发会话数和用户数。
- 结果对注意力架构（全注意力/混合/线性）和上下文使用率假设高度敏感，需做敏感性分析。

**海豚案例**

- Qwen《存力接棒算力，HBM为什么“脱颖而出”？》（2026-09-17）：80%上下文使用率假设下，Qwen3.8 Max单会话缓存约36GB；32个会话时单实例总内存3.6TB（参数2.3TB+KV 1.3TB）。
- NAND《从绿叶到鲜花，AI 推理如何为 NAND「逆天改命」？》（2026-09-30）：写出KV Cache总量=上下文长度×并发会话数×单Token存储量，上下文4K→128K→1M+，并提示KDA、TurboQuant等压缩算法会下修单Token存储量。

**适用场景与注意事项**：适用于推理侧内存需求建模。必须同时考虑压缩算法对单Token存储量的下修，并在报告里明示上下文使用率假设。

### 3.2.5 应用架构放大器与“剪刀差”：RAG、Agentic Search、Multi-Agent 与HBM扩容速度赛跑

**方法要点**：并发与推理轮次被三种应用架构放大；再把“上下文每年翻倍”的需求曲线与HBM单卡容量2-3年翻倍的供给曲线对比，两条曲线的剪刀差就是“必须向下层卸载”（到DRAM/NAND）的论据。

**操作步骤 / 拆分口径**

1. 列出三种放大器：
   - RAG：检索文档拼接进输入，单次任务Token远超原问题。
   - Agentic Search：规划→调用→评估→再检索循环，单次Token从数百拉到上百万。
   - Multi-Agent：多个Agent各自生成KV Cache，成倍叠加。
2. 供给侧对比：模型厂每年至少把上下文扩大一倍，而HBM单卡容量约2-3年才翻一倍且红利放缓。
3. 用两条曲线的剪刀差论证KV Cache“必须向下层卸载”，需求向DRAM/NAND外溢。

**关键指标与数据来源**：上下文长度增速、并发会话数、单Token KV字节数、HBM单卡容量翻倍周期（2-3年）。

**判断标准**：需求曲线（每年翻倍以上）斜率大于供给曲线（2-3年翻倍），差值越大，向下层介质卸载的必要性越强。

**海豚案例**

- NAND《从绿叶到鲜花，AI 推理如何为 NAND「逆天改命」？》（2026-09-30）：RAG/Agentic Search/Multi-Agent三种放大器；上下文每年翻倍 vs HBM 2-3年翻倍。

**适用场景与注意事项**：适用于AI推理带动的内存、存储、网络需求测算。需同时考虑压缩算法（如KDA、TurboQuant）对单Token存储量的下修。

### 3.2.6 推理数据读取量随生成token数平方增长（等差数列求和）

**方法要点**：推理时每生成一个新token，都要完整读一遍激活参数和此前全部KV缓存，累计读取量是等差数列求和，随token数平方增长，用来论证带宽需求的增长斜率。

**操作步骤 / 拆分口径**

1. 每生成一个新token，读取一遍激活参数和此前全部KV缓存。
2. 生成n个token就重复n次，累计读取量是等差数列求和，随token数平方增长：上下文多10倍，读取量约增100倍。
3. 代入具体模型：Qwen3.8 Max在已有100k上下文的基础上生成100k个新token，需读取约500TB数据。
4. 解释“参数大增、读写量却下降”的矛盾，两条原因：
   - 模型从“致密”转向“稀疏”（MoE只激活部分参数）。
   - 注意力从“全注意力”转向“混合/线性注意力”（只全量使用最相关的缓存，其余压缩使用）。

**关键指标与数据来源**：激活参数量、KV缓存大小、生成token数、累计读取量（TB）。

**判断标准**：Qwen3参数比前几代大增，读写量却明显下降，说明架构变化会显著改变测算结果，因此应把稀疏化与注意力变化作为带宽需求的修正项。带宽/算力比值的代际追踪见 6.3。

**海豚案例**

- Qwen《存力接棒算力，HBM为什么“脱颖而出”？》（2026-09-17）：100k上下文+100k新token约读取500TB，以及稀疏化与混合/线性注意力使读写量下降的解释。

**适用场景与注意事项**：适用于论证带宽需求的增长斜率。模型架构变化会显著改变测算结果。

### 3.2.7 杰文斯悖论：软件效率提升被更大模型和更多用户“吃回”

**方法要点**：稀疏化、线性注意力、低精度等软件技术会降低单位硬件需求，但新一代模型会用更大的参数和更长的上下文把省下来的资源重新用满，再叠加用户数爆发，总需求不降反升。这是应对“效率提升会降低硬件需求”空头论点的标准论证。

**操作步骤 / 拆分口径**

1. 列出效率提升项：稀疏化、线性注意力、低精度等，承认其降低单位需求。
2. 论证“吃回”：新一代大模型用更大参数（数万亿乃至十万亿量级）和更长上下文，把省下来的硬件资源重新用满。
3. 叠加Agent和Coding时代的用户数、会话量爆发：“单用户用量×用户数量”双增共振。
4. 结论：存力总需求成倍增长。

**关键指标与数据来源**：模型参数规模、上下文长度、用户数、会话量、单用户token用量。

**判断标准**：成立的前提是需求弹性确实大于1，即单位成本下降带来的用量增长大于效率提升幅度，需要用实际数据验证。

**海豚案例**

- 《存力接棒算力，HBM为什么“脱颖而出”？》（2026-09-17）：以杰文斯悖论回应稀疏化、线性注意力、低精度带来的需求下降论点，论证“单用户用量×用户数量”双增共振。

**适用场景与注意事项**：适用于AI硬件需求的多空辩论（如DeepSeek式效率冲击）。要验证需求弹性确实大于1，否则悖论不成立。

### 3.2.8 逐品类识别AI带来的“新增使用场景”，再据此选测算变量

**方法要点**：测算需求前，先识别每类产品在AI中的新场景，场景识别决定后面测算选哪些变量。

**操作步骤 / 拆分口径**

1. DDR：
   - CPU侧系统内存（数据预处理、模型调度、参数分发）。
   - 2025年新增的CXL扩展内存池，充当“外挂仓库”，协助模型卸载和存放KV Cache，分担HBM压力。
2. NAND：
   - 替代交期过长的HDD。
   - Rubin新增推理上下文存储平台ICMS（每GPU扩展16TB，把KV Cache从HBM下沉到NAND）。
3. HBM：完全由AI GPU“从无到有”创造的需求，与AI芯片出货直接挂钩。
4. 池化方向：CXL交换芯片做DRAM池化，英伟达CMX做NAND池化。
5. 把识别出的场景映射到测算变量：单机配置量、渗透率、新平台规格。

**关键指标与数据来源**：各场景的单机配置量、渗透率、新平台规格。

**判断标准**：按“有没有新场景—需要什么变量—变量能否挂钩现有出货量”三步选变量，例如HBM直接挂钩AI芯片出货，NAND新增量挂钩ICMS的每GPU扩展容量。

**海豚案例**

- 《存储猛拉，AI存力超级周期到底有多神？》（2026-01-06）。
- 《老黄解锁Rubin，AI存储又添“一把火”》（2026-01-07）。
- 《99%计算闲置？推理时代，存力比算力香！》（2026-01-14）。
- 《从HBM限高到NAND加量，英伟达vs存力到底谁拿捏谁？》（2026-09-29）：CXL DRAM池化、CMX NAND池化。

**适用场景与注意事项**：适用于新技术带来增量需求的元件行业。新场景早期的渗透率不确定性大。

### 3.2.9 用一个具体用户任务走一遍两种产品形态的算力调用链（聊天机器人 vs 常驻Agent）

**方法要点**：用一个具体任务（监控Mac mini价格）把两种产品形态的算力调用链逐步走一遍，找出新形态相对旧形态多出来的硬件负载（常驻运行的CPU）。

**操作步骤 / 拆分口径**

1. 传统聊天机器人：请求→GPU推理→回答“好的”→结束→CPU闲置，第二天再问一切重来。
2. Muse：请求→GPU推理→CPU设置监控脚本→VM持续运行（用户关掉App后VM仍在云端跑）→每天查一次price API，一个月30次，每次都是GPU推理判断加CPU执行工具→30天后价格降到899美元，CPU监控脚本发现→唤醒GPU做下单决策→CPU操控浏览器填地址、填信用卡、点下单。
3. 对比后识别出“持续运行”这块新增CPU负载。
4. 再与OpenClaw对比：Muse给每个用户配一台独立的云端Linux VM（2 vCPU），OpenClaw默认在本地运行，这个差异正是云端CPU增量的来源。

**关键指标与数据来源**：每个任务的GPU调用次数、CPU执行次数、VM常驻时长、vCPU配额。

**判断标准**：新形态里CPU执行次数、VM常驻时长越长、vCPU配额越大，对云端CPU的增量越大；本地运行的产品不产生云端CPU增量。

**海豚案例**

- Muse/CPU《Muse“爆火”…》（2026-09-28）：“监控Mac mini价格”任务的算力调用链对比，识别常驻VM的CPU增量，并以OpenClaw作对照。

**适用场景与注意事项**：适用于对新AI产品形态做算力需求定性。要先把产品的技术细节（如VM配置）查清楚。定性结果之后再接 3.3.10-3.3.12 的CPU量化测算。

### 3.2.10 对比芯片晶体管分配并拆解Agent工作流，确定GPU与CPU的分工

**方法要点**：从芯片架构本身（晶体管花在哪）和工作流各环节出发，判断一种新负载应该落在哪种芯片上，论证Agent负载对CPU的刚性需求。

**操作步骤 / 拆分口径**

1. 对比晶体管分配：GPU几乎把晶体管全用在算术单元上；CPU则把大部分晶体管花在管理控制上，包括分支预测器、乱序执行窗口、预取器、多级缓存。
2. 拆Agent工作流：感知→规划→推理→工具执行→验证→再规划→再执行，GPU只负责“推理”这一小段，其余都得靠CPU。
3. 对比两种场景：
   - 纯推理场景：CPU只做分词、把请求交给GPU、再把结果拼回来。
   - Agentic场景：CPU是指令层，负责规划任务、拆子任务、调度并行的子智能体、管理工具调用和API请求、监控token流、整合结果、跑反思循环。
4. 沙箱安全隔离也落在CPU上：CPU的隔离能力来自指令集和硬件结构，几十年积累了一整套专门电路。

**关键指标与数据来源**：工作流各环节对应的芯片、硬件隔离能力。

**判断标准**：工作流里非推理环节占比越高、隔离要求越强，对CPU的需求越刚性。

**海豚案例**

- Muse/CPU《Muse“爆火”…》（2026-09-28）：晶体管分配对比与Agent工作流拆解，得出Agent负载对CPU有刚性需求。

**适用场景与注意事项**：适用于判断一种新负载对不同芯片的需求怎么分配。

### 3.2.11 逐步解读厂商官方架构图，找出“需求乘数”和新增硬件所在位置

**方法要点**：对龙头厂商给出的官方架构图逐步读，把“目标—拆分—往返—编排”每一步对应到硬件，找出放大需求的乘数以及新增硬件出现在哪些位置。

**操作步骤 / 拆分口径**

1. 读ARM给出的AI agent工作流图：
   - 用户向agent提出的是一个目标，不是一个问题。
   - agent本体跑在云端CPU上，这一层没有加速器。
   - 一个agent把任务拆成多个子agent（图上是12个），这是整张图的需求乘数。
   - agents和AI数据中心之间是双向箭头，每个agent各有一对，代表“想-做-看”的反复往返，而不是一次调用。
   - 数据中心里的编排CPU（Agentic CPU，新增需求）负责接请求、管状态、调度，把要推理的部分喂给加速器，再回到CPU判断下一步。
2. 特别区分：这里的编排CPU负责agent主循环（拆任务、生成子agent、持有状态、决定反思和重试、分发工具调用），不是推理服务里靠近GPU的头节点CPU。
3. 再对照英伟达AI工厂图，确定Vera CPU出现在三个位置：
   - VR NVL72（头节点）。
   - Vera CPU机架（独立CPU机架，256颗×88核）。
   - Vera BlueField存储（STX，负责存储管理、DPU和KV Cache持久化）。

**关键指标与数据来源**：子agent数量、Vera CPU机架核数（22,528）、STX机架CPU数量；来源为ARM、英伟达官方架构图和发布材料。

**判断标准**：图中“一对多”的拆分关系是需求乘数；“双向反复往返”意味着是持续负载而非一次调用；新增硬件位置越多，增量需求来源越广。

**海豚案例**

- Muse/CPU《Muse“爆火”…》（2026-09-28）：逐步解读ARM的agent工作流图，并对照英伟达AI工厂图确定Vera CPU的三个位置。

**适用场景与注意事项**：适用于从产业龙头的官方材料里提炼需求结构。厂商材料带有宣传成分，要打折看；量化落地见 3.3.11、3.3.12。

### 3.2.12 储能需求驱动拆解：政策经济性、AIDC刚性需求、光储平价、海外关税与IRA约束、产品LCOE优势

**方法要点**：把储能需求按驱动因素分层拆开，每一层都用可量化指标（IRR、关税税率、能量密度、LCOE）验证，再以大行全球需求预测为基准，给出公司出货预测。

**操作步骤 / 拆分口径**

1. 政策层：国家层面的独立储能容量电价机制（114号文，全国统一储能容量电价机制），用IRR提升（至8-9%）量化项目经济性；国内独立储能“容量电价+现货套利+辅助服务”跑通。
2. AIDC层：
   - 电源侧：风光配储提升新能源有效容量系数。
   - 用户侧：平抑AI负载毫秒级功率脉冲、削峰填谷套利。
   - 北美电网（PJM、ERCOT）要求大负荷具备调节能力，配储有助加速并网。
3. 光储平价：让储能从政策驱动转向市场驱动。
4. 海外约束：美国关税（中国ESS电池2026年加征至48.4%）与IRA外国组件限制（2026/2027年分别不超过45%/40%）下的进入空间。
5. 供给端产品力：587Ah电芯、434Wh/L，系统能量密度+25%，降低客户度电成本（LCOE）。
6. 给出全球需求增速预测，以大行全球需求预测为基准，叠加已发出未确收存货，给出公司储能出货预测。

**关键指标与数据来源**：储能项目IRR、容量电价政策、全球储能需求/电池需求（GWh）、风光新增装机、关税税率、IRA比例、电芯规格与能量密度、LCOE。

**判断标准**

- 政策拐点：容量电价机制建立使IRR提升至8-9%，项目从“政策驱动”转向可自我造血。
- 国内装机延续60%以上高增，全球需求预期随时点推移从+57%至693GWh（3月，大行预测）抬升到+86%、突破1TWh（7月），说明多层驱动叠加有效。
- 海外要看关税和IRA对中国产品的实际进入空间。
- 产品LCOE优势决定份额，而不仅是总量。

**海豚案例**

### 3.3.1 存储需求三分法（常规终端/通用服务器/AI服务器），统一折算为Gb口径

**方法要点**：把DRAM总需求（含HBM、不含库存变化）分成常规终端、通用服务器、AI服务器三块，全部折算成bit（Gb）口径以便加总；先给总量与结构结论，再分项展开“出货×单机容量”。

**操作步骤 / 拆分口径**

1. 分三块：
   - a. 常规产品（PC、手机、平板、汽车、电视等）。
   - b. 传统/通用服务器的常规DDR。
   - c. AI服务器的DDR与HBM。
2. 全部折算为bit（Gb）口径，才能直接加总，并计算结构占比与增量贡献。
3. 先给结论：2025年约3360亿Gb→2028年约5490亿Gb，CAGR约18%。
4. 再给结构：增量贡献中通用服务器、AI服务器DDR、HBM各约1/3，常规产品仅约3%；服务器（含AI）在总需求中的占比从约34%升至约59%。
5. 然后逐块展开测算（见 3.3.2、3.3.3、3.3.4）。

**关键指标与数据来源**：各终端出货量、单机DRAM容量（GB）、bit需求（Gb）、需求结构占比、增量贡献。

**判断标准**：总量CAGR约18%，但增量几乎全部来自服务器侧（通用服务器、AI服务器DDR、HBM各约1/3），常规产品仅贡献约3%，说明需求结构正在从消费电子主导转向服务器主导。

**海豚案例**

- 《海力士：超级AI加持，存储神话还能牛多久？》（2026-10-08，第1.1节）：2025年约3360亿Gb→2028年约5490亿Gb；增量三分天下；服务器占比约34%→约59%。

**适用场景与注意事项**：适用于存储、被动元件、功率器件等多下游元器件行业的需求建模。注意不含库存变化，需求≠出货≠供应。

### 3.3.2 常规终端需求 = 出货 × 单机容量，识别涨价挤出效应并定性为“缓冲垫”

**方法要点**：常规产品需求由“出货量（取市场预期）×单机容量”测算，并识别涨价对需求的挤出，把被挤出的需求定性为“推迟而非消失”，作为下行周期的托底。

**操作步骤 / 拆分口径**

1. 出货量采用市场预期：2026年PC和手机出货均下滑约10%，2027年再降约5%-7%。
2. 单机容量判断为刚性、不太会下降，以确保使用体验。
3. 识别挤出机制：内存大涨价使存储占手机物料总成本（BOM）比重普遍翻倍，压制出货。
4. 定性：被挤出的需求是“推迟而非消失”，价格回落后释放，为下行周期托底，即“缓冲垫”。
5. 列出双向风险：涨价持续则挤出更大；端侧AI落地则单机容量明显提升。

**关键指标与数据来源**：PC/手机出货增速、单机DRAM容量、存储占BOM比重。

**判断标准**：常规产品需求在2026-28年约2160亿-2260亿Gb原地踏步，占比约66%→41%，说明它不再是增量来源，但在下行周期里对价格形成支撑。

**海豚案例**

- 《海力士：超级AI加持，存储神话还能牛多久？》（2026-10-08）：常规产品需求2026-28年约2160亿-2260亿Gb原地踏步，占比约66%→41%；涨价挤出被定性为“缓冲垫”。

**适用场景与注意事项**：适用于上游涨价对下游需求的价格弹性分析，也可用于判断下行周期的需求托底。

### 3.3.3 通用服务器需求 = 出货增速 × 单机内存用量，并用历年主流服务器参数表验证

**方法要点**：量（出货增速）和价（单机内存用量）分别预测，再用历年主流服务器配置表验证单机容量路径，得出“常被忽视但同样重要”的增量。

**操作步骤 / 拆分口径**

1. 量：疫情期间采购的服务器进入更换期，叠加Agent带来的通用算力（CPU）需求，2026-28年出货增速回升至约15%。
2. 单机用量：业内预测2025-28年单机DDR用量每年提升7%-10%，从约800G到超1TB。
3. 验证：整理历年主流服务器参数，确认单机配置容量从24-25年的大几百GB→27-28年1TB起步。
4. 结论：通用服务器DDR需求约760亿Gb→1480亿Gb，三年翻倍，CAGR约25%。

**关键指标与数据来源**：通用服务器出货、换机周期、单机内存容量；历年主流服务器配置参数。

**判断标准**：量（约15%）与单机用量（7%-10%/年）叠加，CAGR约25%，验证路径是主流服务器的配置参数是否朝1TB起步演进。

**海豚案例**

- 《海力士：超级AI加持，存储神话还能牛多久？》（2026-10-08，第1.1b节）：通用服务器DDR约760亿Gb→1480亿Gb，三年翻倍。

**适用场景与注意事项**：适用于服务器相关零部件（CPU、内存、SSD、电源、PCB）需求测算。

### 3.3.4 AI服务器内存需求 = XPU颗数（受CoWoS约束）× 单颗HBM + 单颗对应主机DDR + 其他节点附加

**方法要点**：把出货口径从整机切换为XPU颗数，并用台积电CoWoS产能约束出货上限，再分别测算单颗HBM、单颗对应主机DDR，最后补上难以逐一预测的其他节点。

**操作步骤 / 拆分口径**

1. 出货：口径从整机切换为XPU颗数，结合台积电CoWoS产能约束，测算全球AI加速芯片从2025年约1090万颗→2028年约3170万颗（CAGR约43%）；拆英伟达与ASIC，ASIC从约400万→1780万颗，2027年起超过英伟达。
2. 单颗HBM：继续堆层数工艺难度与晶圆损耗上升，单颗容量上限已不涨（Rubin与GB300持平，Rubin Ultra可能从288GB降至192GB），但有结构性提升：
   - ASIC向GPU看齐（192→288GB）。
   - AMD以更多颗HBM错位竞争（MI455X达432GB）。
   - 出货加权后每颗XPU HBM年化约+14%。
3. 单颗DDR：以B200为例，每8颗GPU配2颗x86 CPU、2TB内存，每颗GPU对应256GB；CPU:GPU比从1:4（B200）升至1:2（VR系列），每颗XPU主机内存约220GB→290GB。
4. 不带HBM的推理服务器、CPU计算节点、存储节点难以逐一预测，按该类DDR需求的约1/4-1/3额外计入。

**关键指标与数据来源**：CoWoS产能、XPU出货（英伟达/ASIC/AMD）、单颗HBM容量、CPU:GPU配比、单机主机内存。

**判断标准**：AI服务器总需求约390亿→1760亿Gb，贡献增量近2/3；其中HBM约155亿→780亿Gb（CAGR约71%），AI服务器DDR约240亿→980亿Gb。

**海豚案例**

- 《海力士：超级AI加持，存储神话还能牛多久？》（2026-10-08）：AI服务器总需求约390亿→1760亿Gb，贡献增量近2/3；HBM约155亿→780亿Gb，AI服务器DDR约240亿→980亿Gb。

**适用场景与注意事项**：适用于AI产业链零部件需求测算。注意口径切换（整机→XPU颗数）与上游瓶颈（CoWoS）的约束作用。

### 3.3.5 HBM需求链式测算：CoWoS产能 → AI芯片出货 → 单芯片HBM容量

**方法要点**：HBM基本都配在AI芯片上，而AI芯片都要用CoWoS封装，所以需求按“CoWoS→AI芯片→HBM”推导，最后与供给对比得出供需结论。

**操作步骤 / 拆分口径**

1. CoWoS总量：列出主要客户的分配量（英伟达占一半以上，谷歌、AMD、亚马逊也是大客户），假设所列核心客户占90%，推出2026年全球CoWoS需求约128万片。
2. 每片CoWoS产出的芯片数：以B300为例，单片CoWoS约得14个B300（28个裸芯），35万片约对应490万个B300。
3. 单芯片HBM含量：B300配8颗HBM3E、每颗36GB，共288GB，490万颗需约14亿GB。
4. 对谷歌、AMD等各家芯片同法加总，128万片CoWoS约对应42亿GB。
5. 持续跟踪主流AI芯片的HBM代际与配置（当前多为HBM3E，三家已送样HBM4）。
6. 与供给41.9亿GB对比，得出紧平衡。

**关键指标与数据来源**：CoWoS分客户分配量（万片）、单片CoWoS芯片数、单芯片HBM颗数×单颗容量、HBM代际。

**判断标准**：2026年供给41.9亿GB vs 需求42.1亿GB，HBM呈“供应紧平衡”。

**海豚案例**

- HBM《存储猛拉，AI存力超级周期到底有多神？》（2026-01-06）：128万片CoWoS→约42亿GB HBM需求，对比供给41.9亿GB，得出紧平衡。

**适用场景与注意事项**：适用于高度绑定上游封装产能的配套元件（HBM、基板、散热等）的需求测算。CoWoS分配是市场预期，可能随客户调整而变。

### 3.3.6 AI服务器DDR需求：单CPU DDR含量 × 每柜CPU数 × 机柜数，按产品代际混合取均值

**方法要点**：从新平台规格推导单柜DDR，再按代际混合比例取均值，乘以CoWoS约束下的机柜数，得出AI服务器DDR需求和对整体供应的侵蚀程度。

**操作步骤 / 拆分口径**

1. 取单CPU含量：Rubin的Vera CPU单颗DDR（LPDDR5X）1.5TB，是Grace的3倍。
2. 单柜含量：NVL72含72颗GPU和36颗CPU，单柜DDR约54TB（Blackwell约18TB）。
3. 按代际混合：按市场预期，2026年英伟达CoWoS在B300和Rubin之间约1:1，取均值，单柜约36TB，即每颗GPU约0.5TB DDR（略好于市场预期）。2027年出货集中在Rubin，单CPU含量升至1.5TB。
4. 结合CoWoS总量（2026年按市场预期，2027年约190万片）推出AI服务器DDR需求：2026年约80亿GB（《老黄解锁Rubin》一文口径为91.9亿GB、同比+250%，比市场原预期多约1EB），2027年144亿GB以上（+80%）。
5. 衡量对整体供应的侵蚀：2026年AI服务器DDR增量约66亿GB，占DRAM整体供应15-20%，直接侵蚀PC和手机的供应。

**关键指标与数据来源**：单CPU DDR容量、单柜CPU/GPU数、产品代际组合比例、CoWoS片数→机柜数、DDR需求（GB/EB）及占总供应比例。

**判断标准**：AI服务器DDR增量占DRAM整体供应的15-20%，意味着对传统领域供应形成挤占，是供需失衡的主要来源之一。

**海豚案例**

- 英伟达Rubin《老黄解锁Rubin，AI存储又添“一把火”》（2026-01-07）：Vera 1.5TB、NVL72单柜54TB，AI服务器DDR 91.9亿GB口径。
- 《99%计算闲置？推理时代，存力比算力香！》（2026-01-14）：2026年约80亿GB，2027年144亿GB以上（+80%）。

**适用场景与注意事项**：适用于从新平台规格推导配套元件需求（内存、SSD、光模块、电源等）。关键假设是产品组合比例和CoWoS预期。同一作者不同篇的口径有差异（91.9亿GB vs 80亿GB），引用时要注明口径。

### 3.3.7 NAND需求分下游测算：AI服务器（Rubin增量+其他AI服务器）+ 手机/PC + 传统服务器 + 工业

**方法要点**：NAND需求按下游分块加总，AI服务器再拆成“Rubin新增量”和“其他AI服务器”，最后观察最大下游是否发生切换。

**操作步骤 / 拆分口径**

1. AI服务器拆两部分：
   - Rubin增量：35万片Rubin CoWoS对应的GPU数×每GPU新增16TB，2026年约78EB。
   - 其他AI服务器：B300服务器（以NVL72为例）一般搭载500GB-1.2TB NAND，取中值850GB（原文口径），假设2026年单台需求增长30%，得180EB以上。
   - AI服务器合计：2026年258EB、2027年453EB（+116%、+77%）。
2. 手机/PC：单机NAND容量继续增长，但涨价压制出货，2026-2027年手机、PC需求分别约298EB和187EB，两年仅微增。
3. 传统服务器：假设增长10%。
4. 工业等其他领域：受涨价影响，复合增长5%。
5. 合计NAND需求：2026年1094EB、2027年1325EB，复合增速接近20%。

**关键指标与数据来源**：每GPU NAND扩展容量、单柜SSD容量、AI服务器出货、手机/PC出货与单机容量、各下游增速假设。

**判断标准**：AI服务器将在2027年成为NAND最大的下游应用，这是重要的叙事拐点（“最大下游切换”）。

**海豚案例**

- NAND《99%计算闲置？推理时代，存力比算力香！》（2026-01-14）：AI服务器2026年258EB、2027年453EB；NAND总需求1094EB→1325EB；AI服务器2027年成为最大下游。

**适用场景与注意事项**：适用于需求结构快速变化的存储品类。各增速假设需要滚动跟踪。

### 3.3.8 DRAM总需求三段加总：AI服务器HBM + AI服务器DDR + 传统领域

**方法要点**：公式为 DRAM总需求 = AI服务器HBM需求量 + AI服务器DDR需求量 + 传统领域需求量，三块分别测算，并强调本轮回暖本质上由AI服务器带动。

**操作步骤 / 拆分口径**

1. AI服务器HBM：沿用CoWoS链式测算（见 3.3.5）。
2. AI服务器DDR：单CPU DDR含量×CPU数×机柜数（见 3.3.6）。
3. 传统领域（手机、PC、工业）：单机含量提升，但出货受存储涨价压制，中性假设2026、2027年各增长约5%。
4. 加总：2026年DRAM整体需求约439亿GB（+25%），2027年约542亿GB（+23%）。
5. 归因：本轮DRAM周期回暖本质上由AI服务器带动，造成失衡的更大原因是服务器用DDR，而不是HBM。

**关键指标与数据来源**：AI服务器HBM需求、AI服务器DDR需求、手机/PC/工业DRAM需求及增速。

**判断标准**：失衡的主因是DDR而非HBM，关键敏感项是传统需求的价格弹性（涨价造成的需求破坏）。

**海豚案例**

- DRAM《99%计算闲置？推理时代，存力比算力香！》（2026-01-14）：2026、2027年DRAM需求约439亿GB、542亿GB。

**适用场景与注意事项**：适用于需求可拆成“AI新增+传统成熟”的半导体品类。

### 3.3.9 从下游产品规格推算单位存储需求（自下而上的单机/单柜需求）

**方法要点**：用英伟达等下游产品的具体配置推算存储需求增量，从单颗、单GPU、单机柜逐级放大，并给出代际倍数。

**操作步骤 / 拆分口径**

1. CPU侧：单颗Vera CPU的DDR需求达1.5TB，是Grace的3倍。
2. Rubin CPX：直接选用GDDR7而非HBM，带动DDR类需求。
3. Rubin新增“推理上下文存储平台”（ICMS）：把KV Cache从HBM下沉到更有性价比的介质，每个Rubin GPU可额外扩展16TB NAND，单个NVL72可扩展1152TB NAND需求。
4. 逻辑链：模型重心从训练转向推理→“内存墙”使存力比算力更重要→DDR和NAND需求外溢。

**关键指标与数据来源**：单颗CPU的DDR容量；单GPU的NAND扩展容量；单机柜（NVL72）需求；代际倍数。

**判断标准**：代际倍数（Vera是Grace的3倍）和单柜扩展量（1152TB NAND）是判断增量规模的直接依据，规格变化（例如HBM层数调整）需要持续跟踪。

**海豚案例**

- 美光《美光 MU：AI 带动存储“疯涨”，能破周期“紧箍咒”吗？》（2026-03-19）：Vera 1.5TB（Grace的3倍），NVL72对应1152TB NAND。

**适用场景与注意事项**：适用于AI硬件链需求测算，可迁移到光模块、PCB、电源等。规格可能变化（例如HBM层数调整），需要持续跟踪。

### 3.3.10 需求口径选择：用“单GW CPU核数”，而不用GPU:CPU配比或单GPU核数

**方法要点**：同一种需求常有多种说法（比例、单卡含量、单位电力含量），结构变化期要先选对口径，否则前后不可比。海豚君选“每GW CPU核数”做CPU需求口径。

**操作步骤 / 拆分口径**

1. 列出市场上几种CPU需求说法：GPU:CPU配比、每颗GPU对应的CPU核数、每GW的核数。
2. 逐个检验：
   - GPU:CPU主要描述的是头节点，对Agentic阶段意义不大。
   - 每颗GPU对应的核数，在引入独立CPU机架后必然大幅上升，前后不可比。
   - 每GW核数能在电力约束下把GPU机架和CPU机架放在一起比，还能直接和ARM等厂商的“每GW核数”展望对照。
3. 选口径的三条标准：能覆盖新增品类；不会因为分母结构变化而失真；能和外部展望对照。

**关键指标与数据来源**：每GW CPU核数、单GPU核数、GPU:CPU配比；ARM等厂商的每GW核数展望。

**判断标准**：满足“覆盖新增品类、分母结构变化不失真、可与外部展望对照”三条的口径才可作为主口径；以电力为约束的口径可以把不同形态的机架放在同一尺度下比较。

**海豚案例**

- Muse/CPU《Muse“爆火”…》（2026-09-28）：ARM称传统AI数据中心每GW约需3,000万颗CPU核心，Agentic时代将升至1.2亿；海豚君据此选“每GW核数”作为统一口径。

**适用场景与注意事项**：适用于结构变化期的需求测算口径选择。以电力为约束的口径，对数据中心类需求普遍适用。

### 3.3.11 单GW CPU核数测算：机架功耗 → 机架数 → 每机架核数，按CPU机架占比做保守/中性/乐观情景

**方法要点**：用机架功耗把1GW折成机架数，再乘每机架核数，得出传统AI数据中心与Agentic数据中心的每GW核数，并按CPU机架占比做三档情景，同时校验厂商展望是否高于理论上限。

**操作步骤 / 拆分口径**

1. 传统AI数据中心（以GB300 NVL72为例）：
   - 整机架约130kW，1GW约对应7,692个机架。
   - 每个机架约2,592核（72颗GPU×每GPU 36核）。
   - 1GW约需2,000万核，低于ARM给的3,000万口径。
2. Agentic数据中心：
   - VR NVL72和CPU机架的功耗都在200kW左右，1GW约对应5,000个机架。
   - 再按NVL72和CPU机架的分配比例做保守、中性、乐观三档情景（三档都代表CPU机架带来的纯增量）。
3. 算出理论上限约1.13亿核，低于ARM展望的1.2亿；海豚君合理估算数据中心所需核数提升2-3倍。
4. 中性情景下（CPU机架占机架总数25%），每颗GPU对应的CPU核数从60个升到约160个。
5. 用测算结果校验厂商展望：ARM的1.2亿高于理论上限。

**关键指标与数据来源**：机架功耗（130kW/200kW）、机架数、每机架核数、CPU机架占比。

**判断标准**：自下而上算出的“理论上限”低于厂商展望时，应对厂商展望打折；核数提升取2-3倍的合理区间，而不是直接取厂商上限。

**海豚案例**

- Muse/CPU《Muse“爆火”…》（2026-09-28）：传统AI数据中心1GW约2,000万核（低于ARM的3,000万）；Agentic数据中心理论上限约1.13亿核（低于ARM的1.2亿）；中性情景每颗GPU对应CPU核数60→约160。

**适用场景与注意事项**：适用于以电力为约束的数据中心器件需求测算。功耗和配置要随产品代际更新。

### 3.3.12 Agentic增量CPU需求公式：A头节点 + B固定层（用户侧）+ C弹性层（子Agent侧）

**方法要点**：把Agent带来的增量CPU需求拆成三层：随GPU出货的头节点、随用户数的固定沙箱层、随任务并发的弹性层，并用超售比、峰均比、并发率等参数把它算成具体核数。

**操作步骤 / 拆分口径**

1. 公式：增量CPU需求 = (A) + (B) + (C)
   - (A) 头节点：GPU出货量 × 每GPU头节点CPU核数。
   - (B) 固定层（用户侧）：总注册用户 × 日活率 × （活跃时长/24）× 每用户2 vCPU × 峰均比 ÷ 超售比 ÷ 2（单核两线程）。
   - (C) 弹性层（子Agent侧）：活跃用户 × 任务并发率 × 每个任务沙箱的核数。
2. B固定层的含义：每个用户预先分好的固定沙箱（Muse的2 vCPU），活跃时分到1个物理核（2线程）；空闲时状态写入存储、VM暂停、物理核释放给别人，所以要除以超售比（一台256核服务器可以分出几百上千个vCPU）。
3. C弹性层的含义：只处理活跃用户的任务，并发率是每个活跃用户平均同时跑几个沙箱（子agent）。
4. 代入案例：1亿Muse用户、日活30%、每天活跃3小时、峰均比2、超售比6：
   - B约125万核。
   - 峰值活跃750万（=1亿×30%×3/24×2）；每个沙箱4核、并发率100%，约需1GW配套，在CPU机架占25%时需1,332个CPU机架，C约3,000万核。
   - A = 28.8万颗GPU × 60核 = 1,728万核。
5. 合计：A+B+C = 4,853万核，约为纯GPU机架方案的2.8倍；再加上存储机架DPU等需求，预估CPU核数需求升到原来的约3倍。

**关键指标与数据来源**：注册用户、日活率、活跃时长、峰均比、超售比、并发率、每沙箱核数、GPU出货量。

**判断标准**：A+B+C合计约为纯GPU机架方案的2.8倍，计入存储机架DPU等后约3倍，与 3.3.11 中“核数提升2-3倍”的合理区间互相印证；其中C弹性层占比最大（约3,000万核），说明并发率和每沙箱核数是最敏感的假设。

**海豚案例**

- Muse/CPU《Muse“爆火”…》（2026-09-28）：以1亿用户、日活30%、每天活跃3小时、峰均比2、超售比6为参数，算出A=1,728万核、B≈125万核、C≈3,000万核，合计4,853万核，约为纯GPU机架方案的2.8倍。

**适用场景与注意事项**：适用于测算Agent类应用对云端CPU的需求。关键假设（并发率、每沙箱核数）要持续用产品的实际使用数据校准。

### 3.3.13 统一产品计数口径（NVL144按die、NVL72按GPU），避免链式测算重复计算

**方法要点**：厂商的营销口径常变（按die还是按GPU、按整机还是按芯片），链式测算前必须先把计数单位统一到同一定义，否则会重复计算或漏算。

**操作步骤 / 拆分口径**

1. 遇到厂商口径变化时追溯定义：黄仁勋提到Rubin从NVL144改回NVL72，实质一样，此前的144按die个数计，这次的72按GPU个数计（1个GPU=2个die），测算中统一采用NVL72口径。
2. 类似地，B300按“单片CoWoS约14个芯片，即28个裸芯”换算。
3. 在做CoWoS→芯片→HBM（见 3.3.5）、单柜DDR（见 3.3.6）等链式测算之前，先统一口径。

**关键指标与数据来源**：die数、GPU数、机柜规格（NVL72/NVL144/NVL576）。

**判断标准**：同一实物只能有一种计数口径；换算时记录1个GPU=几个die。

**海豚案例**

- 英伟达《老黄解锁Rubin，AI存储又添“一把火”》（2026-01-07）：Rubin NVL144改回NVL72，实质相同，统一按NVL72（GPU）口径。
- 《存储猛拉，AI存力超级周期到底有多神？》（2026-01-06）：B300单片CoWoS约14个芯片、28个裸芯的换算。

**适用场景与注意事项**：适用于硬件产业链测算。厂商的营销口径常变，要追溯到定义。

### 3.3.14 自上而下AI芯片需求链：客户Capex → 剔除海外 → 服务器/AI服务器/加速器占比 → TAM → ASP → 卡数 → Die数（含CPU）

**方法要点**：从客户的AI/云Capex出发，逐级剔除和乘占比，得到AI GPU金额TAM，再用ASP或算力反推卡数、Die数，并按客户类型分层。

**操作步骤 / 拆分口径**

1. 客户AI/云Capex。
2. 剔除CSP海外支出（国内市场需剔除海外）。
3. × 服务器占比 × AI服务器占比 × 加速器组件占比 → AI GPU金额TAM。
4. ÷ ASP（或用算力反推）→ 卡数 → GPU Die个数。
5. × CPU/GPU个数比 → CPU Die个数 → Die总需求。
6. 只核算推理端（国产芯目前难满足训练）。
7. 客户分层：
   - a. 互联网巨头（阿里、字节、腾讯）。
   - b. 基础模型企业（DeepSeek、MiniMax、智谱等，token消耗量大，有绕过云厂商直接提需求的权利，领先厂商日均token消耗超十万亿）。
   - c. 主权AI（电信运营商、国企、地方政府，来自国家AI基建、数据主权、算力中心）。

**关键指标与数据来源**：CSP Capex及海外占比、服务器/AI服务器/加速器占比、ASP、CPU:GPU比、token消耗。

**判断标准**：各层占比与ASP的假设决定最终卡数；用token消耗和客户分层交叉检验需求来源，三类客户的驱动力不同（商业化、模型训练推理、国家基建）。

**海豚案例**

- 壁仞科技《壁仞：国产“英伟达”，到底“几斤几两”？》（2026-06-18，第2节）：按上述链条（仅推理端、国内市场剔除海外支出）推算，2026年需求约420万颗。

**适用场景与注意事项**：适用于AI芯片、服务器需求的自上而下测算；国内市场需剔除海外支出。

### 3.3.15 链式测算AI算力需求：头部AI Lab收入情景 → 云算力支出（训练+推理）→ 芯片结构 → GW

**方法要点**：当AI云的增量需求绝大部分来自两家头部AI Lab时，可以用两家的收入情景倒推云算力支出，再折算成GW，并加上其他AI Lab的需求。强调这是情景假设，不是预测。

**操作步骤 / 拆分口径**

1. 需求主体：当前AI云的增量需求绝大部分来自两家头部AI Lab，所以AI云需求约等于AI Lab需求。
2. 收入情景：参考OpenAI给出的2030年约2800亿美元营收愿景，保守下调为两家各约2500亿美元；关键假设是从2028年起，两家增速从三位数回落到50%以下的平稳期，且OpenAI的收入会快速向Anthropic看齐（基模能力、Codex与Claude Code的入口差距已基本抹平）。
3. 云算力支出分推理和训练：
   - 推理毛利率从目前约65%小幅升到70%左右（芯片能效提升与单价下降相互对冲）。
   - 训练支出2027年仍接近100%增长，2028年起快速降到30%以下。
   - 据此得出2028年两家的云算力总支出约2500亿美元，约占当年收入的71%。
4. 折算成GW：训练和推理需要的GPU、ASIC、CPU用量不同，不同芯片的单GW收入也不同。
5. 加上其他AI Lab的需求（约为两巨头的15%，不含云厂自用）。
6. 结果：2028年AI算力需求约25.6GW，比2025年增加近23GW。

**关键指标与数据来源**：AI Lab收入与增速、推理毛利率、训练支出增速、云支出占收入比、单GW收入、GW。

**判断标准**：结果对收入情景高度敏感，应做多情景；2028年云算力支出占收入约71%、推理毛利率65%→70%是两个关键校准参数。

**海豚案例**

- 《AI 算力：从盛宴到“剩宴”？》（2026-07-13）：两大AI Lab收入情景到2028年25.6GW的完整推导。

**适用场景与注意事项**：适用于需求由少数大客户主导的算力或基建行业。必须说明这是情景假设，并做多情景。

### 3.3.16 以2024年为基年，按“算力/收入”比例等比例外推传统云需求

**方法要点**：传统云增速不高，但绝对体量仍占多数，必须计入。用基年已上线算力与云收入的比例，按后续传统云收入的增长等比例推算所需算力，可与 3.3.15 的AI算力需求相加得到云总需求。

**操作步骤 / 拆分口径**

1. 确定基年：2024年云厂近100%的收入和算力仍用于传统需求。
2. 算基年比例：以2024年已上线算力与收入的比例为基础。
3. 外推收入：假设AI尤其是AI Agent也会拉动传统算力，2026到2027年传统云收入保持约20%的增速；但企业IT预算总体增长不多，AI投入和传统IT投入此消彼长，2028年后增速明显放缓。
4. 按收入增长等比例推算所需算力。
5. 结果：2028年传统云所需算力约31GW，比2025年增加约10GW。

**关键指标与数据来源**：基年算力（GW）与云收入、传统云收入增速。

**判断标准**：关键假设是2026-2027年约20%的传统云收入增速及2028年后放缓，这些假设决定了算力外推量。

**海豚案例**

- 《AI 算力：从盛宴到“剩宴”？》（2026-07-13）：传统云需求的基年比例法测算，2028年约31GW，比2025年增加约10GW。

**适用场景与注意事项**：适用于存量业务的需求外推。该方法假设单位收入对应的算力强度不变，忽略了效率提升，会使外推结果偏高，需要结合效率变化修正。

### 3.3.17 订单 → 所需算力GW → Capex推算法

**方法要点**：市场主流的需求端Capex估算方法，海豚君简化为五步：由Backlog推所需GW，再用单GW部署成本得新增Capex，加维持性Capex，并与市场预期区间比对。

**操作步骤 / 拆分口径**

1. 未来两年需消化的Backlog = 总额 × 24个月确认比例。
2. 除以每GW年租赁价格，得所需GW。
3. 按1-2年部署周期，扣除前两年已新增GW，得次年需新投产GW。
4. 乘以单GW部署成本（含存储等涨价调整），得新增Capex。
5. 加维持性Capex（按增速外推）。
6. 结果与市场预期区间比对。

**关键指标与数据来源**：Backlog、24个月确认比例、每GW租赁价格（150亿/GW/年）、单GW部署成本（300→350亿）、已新增GW、维持性Capex。

**判断标准**：推算值与市场预期区间的位置关系，决定市场预期是偏高、合理还是偏低；参数（尤其是单GW成本、租赁价格）对结果高度敏感。

**海豚案例**

- 谷歌（2026-07-27）：Backlog 5140亿×50% = 2570亿，按150亿/GW需17GW；25、26年合计新增近8GW，27年需再建9GW×350亿 = 3150亿，加维持性500多亿（增速25%），共约3650亿。

**适用场景与注意事项**：适用于AI算力、数据中心等产能驱动行业；参数对价格高度敏感，需随时更新。

### 3.3.18 自下而上的AI数据中心峰值负荷公式（GPU出货 × TDP × 系统系数 × PUE × 需量系数）

**方法要点**：把GPU出货一步步折算成数据中心接入容量和峰值负荷，并持续跟踪每个参数的演进，用于测算AI算力对电力、散热、电源等配套的需求。

**操作步骤 / 拆分口径**

1. 公式：
   - 数据中心新增接入容量（GW）= GPU出货量 × 单芯片TDP × 系统功耗系数 × PUE。
   - 新增峰值负荷 ≈ 新增接入容量 × 峰值需量系数。
2. 参数定义：
   - TDP：单芯片热设计功耗。
   - 系统功耗系数：GPU以外维持服务器运行的CPU、内存、网络、电源损耗，通常取1.3-1.5。
   - PUE = 数据中心总能耗 / IT设备能耗，代表制冷配电等环境维持成本。
   - 峰值需量系数 = 实际最大负荷 / 设备额定总功率。
3. 跟踪参数趋势：
   - TDP：从H100的700W升到Blackwell（GB200/GB300）的1200-1400W，Rubin预计超过2000W。
   - 集群：从千卡级到十万卡级，Stargate预计部署超45万颗GB200，负荷或超1.2GW。
   - Grid Strategies预计2026年有10个GW级数据中心投运，2030年前规划的数据中心约50%为GW级。
4. 追溯驱动源头：北美四大CSP的Capex，从2023年约1500亿美元升到2025年预计4060亿美元（CAGR超60%）；中国BAT加字节2025年约600亿美元；全球前11大科技巨头从1800亿美元升到近5000亿美元。

**关键指标与数据来源**：GPU出货量、单芯片TDP、系统功耗系数（1.3-1.5）、PUE、峰值需量系数、CSP资本开支、集群规模。

**判断标准**：TDP上升（700W→1200-1400W→2000W以上）与集群规模放大共同推高单个数据中心负荷；参数（尤其是GPU出货和PUE）不确定性较大，需要用 3.3.19-3.3.21 的三条独立路径交叉验证。

**海豚案例**

- 北美电力《AI竞赛终局：电力说了算？》（2026-02-09）：给出拆解公式和各参数的演进数据（TDP、集群规模、CSP Capex）。

**适用场景与注意事项**：适用于AI算力对电力、散热、电源等配套需求的测算。参数不确定性较大，需要交叉验证。

### 3.3.19 三角验证之一：在建和规划容量法

**方法要点**：用数据中心的在运、在建、规划储备容量，加建设周期，推算未来新增容量，作为对 3.3.18 公式结果的独立检验。

**操作步骤 / 拆分口径**

1. 列出存量与储备（UBS数据）：2025年底全球数据中心投运105GW，在建25GW，规划超100GW。
2. 建设周期：无电力和土地约束时通常18-24个月；新云（如CoreWeave）凭借更快拿到GPU和模块化预制，可缩短到12-18个月。
3. 全球推算：假设125GW储备在2030年前全部投运且不再新增，全球将从105GW增至225GW，5年CAGR约16%。
4. 美国推算：2025年底在运44GW、在建10GW、规划约70GW，2026-2030年释放80GW（占全球增量64%），总量增至124GW，CAGR约23%。
5. 假设AI数据中心高并发高负载，新增容量100%转化为峰值负荷，即80GW的新增峰值负荷冲击。

**关键指标与数据来源**：在运、在建、规划容量（GW），建设周期，容量CAGR，容量转峰值负荷比例。

**判断标准**：规划项目可能取消或延期，应作为上限参考；在建容量加建设周期给出确定性较高的下限。

**海豚案例**

- 北美电力《AI竞赛终局：电力说了算？》（2026-02-09）：美国2026-2030年新增80GW，占全球增量64%。

**适用场景与注意事项**：适用于产能扩张类测算。

### 3.3.20 三角验证之二：资本开支反推容量（单GW建设成本加芯片架构混合加权）

**方法要点**：从资金端反推容量假设是否合理：用单GW建设成本（按芯片架构混合加权）把容量换算成资金需求，再与CSP的Capex预期比对。

**操作步骤 / 拆分口径**

1. 单GW成本：参考黄仁勋口径，1GW数据中心建设成本约500-600亿美元（其中芯片系统约350亿美元），取中值550亿美元/GW（全英伟达方案）。
2. TPU方案：Google TPU v7单位算力TCO比GB300便宜41%，在能耗和散热上也有优势，Capex约为GPU方案的一半（约275亿美元/GW）。
3. 混合加权：按未来5年平均“65% GPU加35% TPU”的混合架构，单GW成本约454亿美元。
4. 反推资金：若未来5年新增80-120GW，年均AI投入约7000亿到1万亿美元。
5. 折算CSP总Capex：若AI数据中心占CSP资本开支的80%-90%，则2026-2030年CSP年均总Capex约9000亿到1.2万亿美元（2026年约6500-7000亿美元），5年CAGR约25%。
6. 与产业链高斜率增长预期比对：基本吻合，从而验证容量假设。

**关键指标与数据来源**：单GW建设成本（GPU方案与TPU方案）、架构混合比例、AI占CSP资本开支比例、CSP年均Capex。

**判断标准**：容量假设对应的资金需求与CSP Capex预期、产业链增长预期吻合，则容量假设成立；不吻合则需调整容量或成本。

**海豚案例**

- 北美电力《AI竞赛终局：电力说了算？》（2026-02-09）：加权454亿美元/GW，对应CSP年均Capex 9000亿到1.2万亿美元。

**适用场景与注意事项**：适用于用资本开支和单位投资强度交叉验证物理容量假设（数据中心、晶圆厂、电站）。要跟踪自研芯片渗透对单位成本的影响。

### 3.3.21 三角验证之三：监管申报数据（FERC公用事业负荷预测）

**方法要点**：使用美国联邦能源监管委员会（FERC）要求电力公用事业公司每年提交的申报材料（发电能力、电力交换量、峰值负荷预测），这是全美电网规划最底层的“账本”，作为第三方验证。

**操作步骤 / 拆分口径**

1. 取FERC申报的各部门峰值负荷预测增量。
2. 北美公用事业大幅上调未来5年峰值负荷预期，规划总增量166GW：
   - 数据中心约90GW。
   - 工业和制造业回流约30GW。
   - 终端电气化约30GW（住宅热泵、电动车设施等）。
   - 油气采矿约10GW。
3. 与自己测算的AI数据中心增量对比。

**关键指标与数据来源**：FERC申报的分部门峰值负荷增量（GW）。

**判断标准**：FERC口径下数据中心约90GW，落在 3.3.22 给出的80-120GW情景区间内，与自下而上测算和在建规划容量法互相印证；FERC口径同时给出非数据中心的负荷增量（工业约30GW、电气化约30GW、油气采矿约10GW），可用于估算基础负荷。

**海豚案例**

- 北美电力《AI竞赛终局：电力说了算？》（2026-02-09）：FERC口径总增量166GW，其中数据中心90GW。

**适用场景与注意事项**：适用于电力、公用事业行业。监管数据权威但可能偏乐观（公用事业有扩大资产基数的动机）。

### 3.3.22 需求情景构建：对机构预测按落地难度打折，并提示上限风险

**方法要点**：综合三种测算后给出自己的情景，而不是照搬某一机构；对不同来源的预测，按落地难度分别打折，并提示乐观情形可能仍然保守。

**操作步骤 / 拆分口径**

1. AI数据中心新增负荷：悲观、中性、乐观分别为80、100、120GW，并提示乐观情形在巨头蓝图面前可能仍保守（OpenAI规划2033年算力基础设施达250GW）。
2. 基础负荷：FERC预测电气化和制造业回流带来约76GW，但考虑美国电动车普及放缓、制造业回流落地复杂，打折为25、40、60GW（CAGR 0.6%-1.5%）。
3. 合计未来5年北美新增峰值负荷105、140、180GW，对应CAGR 2.4%、3.2%、4%。

**关键指标与数据来源**：各情景新增峰值负荷（GW）、CAGR。

**判断标准**：打折理由要具体（政策退坡、落地复杂度）；上限情景要对照巨头长期蓝图检验保守程度。

**海豚案例**

- 北美电力《AI竞赛终局：电力说了算？》（2026-02-09）：悲观、中性、乐观分别为105、140、180GW。

**适用场景与注意事项**：适用于对多源预测综合取值。

**本节速查清单**

- [ ] 测算方向是否明确（自下而上、自上而下，或两者对照），每一步的单位是否可追溯？
- [ ] 计数口径是否统一（按die还是按GPU、整机还是XPU颗数、GB/Gb/EB），是否注明了引用口径？
- [ ] 需求是否按下游分块（常规终端、通用服务器、AI服务器）分别测算后再加总，并核对了库存是否计入？
- [ ] 是否把上游瓶颈（如CoWoS产能）作为出货上限，并与供给对比得出紧平衡或缺口？
- [ ] 口径选择是否覆盖新增品类、不因分母结构变化失真、能与外部展望对照？
- [ ] 关键假设（并发率、超售比、产品组合比例、收入情景、单GW成本）是否做了多情景和敏感性？
- [ ] 是否用至少一条独立路径（在建规划容量、Capex反推、监管申报）验证了主测算结果？
- [ ] 厂商或机构展望是否与自下而上的理论上限比较并按落地难度打折？
- [ ] 情景（悲观/中性/乐观）的打折理由是否具体，是否提示了上限风险和“这是情景不是预测”？

## 3.4 需求结构拆分与迁移

> 本节导读：需求总量算出来之后，还要回答“这块需求由谁构成、构成正在怎样迁移、迁移意味着什么”——按下游、终端、负载、场景、客户把需求拆开，才能知道谁是增量、谁是拖累，以及结构切换会不会改写客户的决策逻辑与定价机制。研究多下游元器件行业、AI硬件链（存储、CPU）、AI云与模型公司、电力设备时使用。本节前段是通用拆分口径（终端、应用、历史阶段、新下游），中段讲结构迁移的含义（定价锚、选型决策函数、客户分层），后段讲训练→推理、Chatbot→Agent 带来的品类需求结构变化。总量与公式见 3.2-3.3，弹性与透支见 3.5，价格与合约结构见 5.2-5.3，赛道专属的消费结构指标见 16.8。

### 3.4.1 下游需求按终端拆 bit 增速，并逐一归因驱动与断档

**方法要点**：把一个多下游元器件的总需求拆成几个主要终端，每个终端单独写增速和驱动；下行期再逐个终端解释“为什么断档”，并标出最大单一终端的权重，用来判断谁是主要拖累、谁能对冲。

**操作步骤 / 拆分口径**

1. 选定终端口径。以 NAND bit 需求为例，拆成三大终端：手机、PC（Client SSD）、企业级 SSD。
2. 每个终端先写增速，再写驱动（上行期的逻辑）：
   - 手机：看旗舰机容量翻倍。
   - PC：看 HDD 转 SSD 的渗透率，约 50% 升到 90% 以上。
   - 企业级：看云厂商服务器部署。
3. 下行期逐个终端解释断档原因：
   - 消费端：通胀和利率压制换机、疫情透支；PC 出货 2022/2023 年分别 -12%/-10%。
   - 企业级：标准服务器投资进入消化期，企业级 SSD 增速从 +34% 降到 +20%，再到 -33%；AI 服务器当时还不足以对冲。
4. 标出最大单一终端的权重（手机约占 bit 需求 33%），据此判断谁是主要拖累。
5. 把同一框架向前延伸：终篇把终端拆分升级为“AI 与非 AI 两大块”，AI 块再按负载、介质往下拆（见 3.4.11）。

**公式（加权拆解）**：总 bit 需求增速 ≈ Σ（终端 i 的权重 × 终端 i 的增速）；终端 i 的拖累或拉动 = 权重 × 增速。权重大的终端增速变化一个点，对总需求的影响远大于权重小的终端。

**关键指标与数据来源**：各终端 bit 需求增速、终端出货（PC/手机）、SSD 渗透率、终端占 bit 需求比重；来源为厂商披露与产业数据。

**判断标准**

- 上行是否来自结构性驱动（容量翻倍、渗透率提升、云厂商部署）而不是一次性备货。
- 下行期断档要“归因到终端”：消费端是宏观压制加前期透支，企业端是投资消化；每个终端都要写出原因，而不是笼统说“需求不好”。
- 看对冲：新增终端（如当时的 AI 服务器）体量是否足以对冲传统终端的下滑；不足以对冲，则总需求增速下台阶。
- 推理链条：终端拆分→逐个写驱动→下行期逐个归因→标权重→识别主拖累与对冲项。
- 终端权重要随时更新：本轮 AI 之后数据中心已超过手机和 PC（见 3.4.5 中数据中心占比 30%→45%、手机降至约 23%）。

**海豚案例**

- 闪迪《NAND 天性“多产”…》（2026-09-18）：把 NAND bit 需求拆成手机、PC、企业级 SSD。2018—2021 年需求每年 +34%~46%，2022—2023 年骤降至 6%~8%；手机 bit 增速从 2021 年 46% 降到 2022 年 2%；PC 2022/2023 年出货 -12%/-10%；手机约占 bit 需求 33%，是最大单一终端；企业级 SSD 增速从 +34% 到 +20% 再到 -33%；终篇把框架延伸为 AI 与非 AI 两大块。

**适用场景与注意事项**：适用于所有多下游的半导体或元器件行业。终端权重不是常数，需要持续更新；拆分后各终端增速的加权结果应能回算到总需求，否则说明口径（出货口径 vs bit 口径）不一致，口径校验见 3.3。

### 3.4.2 下游应用结构拆分：先确定主导需求来源（以燃机为例）

**方法要点**：先拆下游应用结构、确认哪个下游是主导需求来源，再判断新增需求是直接拉动行业主体，还是只作用于边缘。

**操作步骤 / 拆分口径**

1. 列出行业全部下游应用：燃机下游覆盖发电、工业驱动、舰船动力三大领域。
2. 给出各下游占比，确认主导下游：发电贡献约 64% 的市场需求，占绝对主导。
3. 把新需求归到对应下游：AIDC（AI 数据中心）电力需求属于发电下游。
4. 结论：AIDC 电力需求能直接拉动行业主体，而不是边缘需求。

**公式（推论）**：新需求对全行业的增量贡献 ≈ 该下游占比 × 该下游的增量；主导下游占比越高，新需求对行业整体的拉动弹性越大。

**关键指标与数据来源**：下游应用占比（发电约 64%）。

**判断标准**：主导下游占比越高，新需求对行业整体拉动越直接；若新需求归属的下游占比很小，即使增速很高，对行业整体的拉动也有限，需要谨慎外推。

**海豚案例**

- 燃机《AI 终极瓶颈…》（2026-04-09）：拆燃机下游结构为发电、工业驱动、舰船动力，发电约占 64%，由此确认 AIDC 电力需求直接作用于行业主体。

**适用场景与注意事项**：适用于判断新需求对行业整体的拉动弹性。前提是占比口径稳定（按金额还是按台数/容量）；占比需随周期更新。后续如何把新需求折成设备量，见 3.2-3.3。

### 3.4.3 需求历史阶段划分 + 按用电部门拆结构

**方法要点**：把需求的历史走势划成几个驱动不同的阶段，说明当前是“新周期的拐点”而不是“一次波动”；再按部门拆结构，找出增长核心和底部支撑。

**操作步骤 / 拆分口径**

1. 阶段划分并解释每阶段的驱动（以美国终端用电需求为例）：
   - 高速增长期（1950s-1990s）：战后繁荣、重工业化、居民电气化，CAGR 约 6%。
   - 平台停滞期（1990s-2020s）：互联网泡沫和 2008 年金融危机后增速换挡，重制造转向轻服务，加上节能技术，15 年几乎无增长。
   - 重启增长期（2021 年至今）：IRA 和芯片法案补贴加特朗普制造业回流，再加 AI 数据中心，2021-2024 年平均增速回升到约 1.5%，电价从 2022 年起加速上涨。
2. 按部门拆分用电结构：
   - 商业用电是增长核心，其中数据中心是主力：截至 2024 年底美国数据中心负荷约 35GW，较 2020 年翻番。
   - 工业用电同步复苏：半导体晶圆厂、电池工厂回流提供底部支撑。
3. 把阶段划分与部门拆分合起来，回答“新一轮增长是谁在拉、能否持续”。

**关键指标与数据来源**：全社会用电量 CAGR、电价、分部门（商业、工业、居民）用电量、数据中心负荷（GW）。

**判断标准**

- 阶段之间增速出现台阶式变化（约 6% → 近乎零 → 约 1.5%），且每个台阶都能对应到明确的结构性驱动，才能说是拐点而非波动。
- 重启期的驱动（补贴政策、制造业回流、AI 数据中心）与结构拆分的结果（商业用电中数据中心为主力、工业回流托底）互相印证，说明增长有“主力 + 底部支撑”两层。
- 价格信号（电价从 2022 年起加速上涨）是需求重新紧张的旁证。

**海豚案例**

- 北美电力《AI竞赛终局：电力说了算？》（2026-02-09）：把美国用电需求划分为三阶段（高速增长期、平台停滞期、重启增长期），并按部门拆结构，指出 2024 年底数据中心负荷约 35GW、较 2020 年翻番，工业回流提供底部支撑。

**适用场景与注意事项**：适用于判断需求是否进入新周期。阶段划分依赖对历史驱动的准确归因，驱动若是一次性政策，就不能直接外推为长周期；数据中心负荷的后续测算见 3.2-3.3，电力供给侧见第 4 章。

### 3.4.4 新下游扩散：每个新下游固定回答“需求 + 格局”两问

**方法要点**：对底层技术通用、下游边界持续扩散的平台型赛道，对每个新下游都用同一结构回答两个问题，使多个下游可以横向比较，也能快速落到“行业怎样、公司卡位如何”。

**操作步骤 / 拆分口径**

1. 先把赛道定义为“下游边界持续扩散”型（例如热管理）。
2. 对主下游（汽车）之外的每个新下游（数据中心、储能、人形机器人）固定回答两问：
   - ①这个行业对该技术的需求为什么在增加？（例：功率密度提升、能效政策、风冷转液冷）
   - ②竞争格局如何、公司做了什么？（参与者分布、公司所处层级、收入体量）
3. 每个下游最后都做市场空间测算。
4. 末尾用“行业需求怎样、公司卡位如何”两句话小结。
5. 把各下游的小结并排，横向比较需求强度与公司卡位。

**关键指标与数据来源**：各下游需求驱动因素；竞争格局；公司参与环节和收入；各下游市场空间。

**判断标准**：两问的答案要能合成一句判断。例如“需求处于爆发式增长阶段，公司参与了但参与得还不算多、以零部件为主”——前半句来自问 ①，后半句来自问 ②。需求强、卡位弱的下游是后续弹性所在，需求强、卡位也强的下游是当期业绩来源。

**海豚案例**

- 三花智控《三花：AI 机器人时代…》（2026-01-08，第一部分）：数据中心、储能、人形机器人三个下游按同一结构展开（需求驱动 → 竞争格局与公司位置 → 市场空间），小结为需求处于爆发式增长阶段、公司参与了但参与得还不算多、以零部件为主。

**适用场景与注意事项**：适用于底层技术通用、下游多元的平台型公司（热管理、连接器、功率半导体等）。两问结构只是固定骨架，市场空间测算的具体方法见 7.2，竞争格局展开见第 8 章。

### 3.4.5 需求结构迁移 → 客户决策逻辑与定价锚迁移 → 长协可行性与风险集中度

**方法要点**：不止报“占比从多少到多少”，而要推导结构变化的含义——主导客户换了，决策函数就换了，进而定价机制（现货/长协）和周期波动性都跟着变。链条为：需求结构 → 客户议价行为 → 定价机制 → 周期波动性。

**操作步骤 / 拆分口径**

1. 按终端拆总需求，跟踪各终端占比的变化，找出“谁成了最大基本盘”。
2. 分析主导客户的决策函数：
   - 消费电子：对价格高度敏感，库存大起大落。
   - 云厂商：以 TCO（总拥有成本）和算力回报 ROI 决策，对价格脱敏，关心“能否按时拿到足额高性能 eSSD，保证未来三年 GPU 基建不掉链子”。
3. 推导议价与合约含义：由“短期压价”转向“长期保供”，构成原厂推行 NBM（新型长协模式）的需求侧基石。
4. 推导定价锚含义：定价锚从消费电子换成云厂商资本开支——买家更有钱、涨价更易传导，但需求更集中，一旦 AI 投资降温冲击更剧烈。
5. 同时对比分品类增量（Gb），避免只看单一品类：例如用服务器 DDR 增量与 HBM 增量比较，判断“紧缺”是否只在 HBM。

**变体 A：NAND——数据中心占比切换 → TCO/ROI 决策 → NBM 长协**

- 数据中心占比由 2025 年约 30% 跃升至 2026 年约 45%，历史性反超手机（收缩至约 23%），成为最大基本盘。
- 需求侧基石：客户由“短期压价”转向“长期保供”，原厂才有条件推行 NBM。

**变体 B：DRAM——服务器占比升至约 59% → 定价锚迁移与风险集中度**

- 服务器占比升至约 59%，意味着行业定价锚从消费电子换成了云厂商资本开支：买家更有钱、涨价更易传导；但需求更集中，AI 投资一旦降温冲击更剧烈。
- 增量对比：服务器 DDR 增量约 1450 亿 Gb，是 HBM 增量约 620 亿 Gb 的两倍多 → “紧缺不只在 HBM”，常规 DRAM 同样紧缺。

**关键指标与数据来源**：按终端拆分的需求占比（数据中心/手机/PC/服务器）、客户类型、分品类增量（Gb）、长协（NBM/LTA）推行情况；CapEx 跟踪数据见 3.1。

**判断标准**

- 定价权改善的前提：大客户真正把供应保障置于价格之上。判断依据是占比切换（数据中心成为最大基本盘）加上客户行为证据（长协签订、保供诉求）。
- 风险的另一面：需求越集中，周期波动越取决于单一客户群的资本开支；若算力投资放缓，客户可能重回压价，需持续追踪 CapEx。
- “增量对比”用于纠偏叙事：热点品类（HBM）之外，体量更大的常规品类（服务器 DDR）同样出现紧缺。

**海豚案例**

- NAND《从绿叶到鲜花，AI 推理如何为 NAND「逆天改命」？》（2026-09-30）：数据中心占比 30%→45%，手机降至约 23%；云厂商从压价到保供，支撑 NBM 长协，推出“需求结构 → 客户议价行为 → 定价机制（现货/长协）→ 周期波动性”的链条。
- 海力士《海力士：超级AI加持，存储神话还能牛多久？》（2026-10-08，第 1.1d 节）：服务器占比升至约 59%，定价锚从消费电子换成云厂商资本开支，涨价更易传导但冲击更集中；服务器 DDR 增量约 1450 亿 Gb、是 HBM 增量约 620 亿 Gb 的两倍多，说明紧缺不只在 HBM。

**适用场景与注意事项**：适用于判断上游零部件行业定价权是否改善（存储、光模块、PCB 等），以及下游从 C 端转向 B 端/云厂商的行业，用于判断涨价传导能力与周期波动幅度。前提是大客户真正把供应保障置于价格之上；合约结构与价格持续性的进一步判断见 5.3。

### 3.4.6 客户选型决策函数：性能（刚性）> 交付周期 > LCOE > ESG

**方法要点**：从买方视角给出选型优先级排序，作为评价技术路线的统一标尺——先看哪些条件是一票否决，再看哪些是关键竞争要素，最后才是成本和 ESG。排序一旦定出，就逐项筛选候选技术。

**操作步骤 / 拆分口径**

1. 供电性能（刚性约束，不满足即一票否决）：7×24 连续稳定，且需匹配 AI 负载毫秒级 40%-100% 的功率波动。
2. 交付周期（关键竞争要素）：AI 芯片折旧极高，数据中心空置等电的机会成本巨大，用户愿为更短交付付显著溢价，交付速度甚至比绝对成本更关键。
3. 经济性（长期运营核心）：用全生命周期度电成本 LCOE 衡量，综合初始投资、燃料、运维、利用率、寿命。可写成 LCOE ≈ 全生命周期总成本 ÷ 全生命周期发电量。
4. ESG：四大云厂商承诺 100% 可再生，并倾向“证电合一”。
5. 定出排序后，用这套决策函数逐项筛选候选技术路线，淘汰不满足刚性约束者，再按交付与 LCOE 比较。

**关键指标与数据来源**：功率波动幅度与响应时间、交付周期、LCOE、绿电属性。

**判断标准**

- 总原则：可靠性保底、交付优先、TCO 最优。
- 优先级是顺序判断而不是加权平均：性能不过关直接出局；性能达标者里，交付周期短的优先于 LCOE 低的。
- 权重会随周期动态变化：缺电紧迫期“交付”权重高；供给缓解后 LCOE 权重回升。

**海豚案例**

- 燃机/电源《AI 终极瓶颈…》（2026-04-09）：用“可靠性保底、交付优先、TCO 最优”原则把四项选型标准按优先级排序（性能 > 交付周期 > LCOE > ESG），作为评价各类电源技术路线的统一标尺。

**适用场景与注意事项**：适用于 B 端设备选型分析。注意权重要动态调整，不能把缺电期的“交付第一”当成永久结论；技术路线的经济性比较见 6.4，供给瓶颈与交付周期约束见 4.4。

### 3.4.7 企业端（看质量）vs 个人/C 端（看价格）：需求分层与分别追踪

**方法要点**：把模型需求分成两个决策逻辑不同的阵营，各用一个最贴近的指标追踪，再看两阵营的交汇场景，判断模型厂的定价权与客户结构。

**操作步骤 / 拆分口径**

1. 企业端：极其看重模型质量，用 ARR 月环比追踪。
   - Anthropic ARR 一超多强；Opus 4.6 发布后，ARR 月均环比从 25Q4 的 9% 飙至 2026 年 1-2 月的 25%，3-6 月保持 30% 以上。
2. 独立 C 端（个人与中小团队）：价格第一，用 OpenRouter 渠道的 Token 用量份额（中/美）和 Token 单价追踪。
   - 中国大模型凭性价比加开源，Token 用量占比持续上升，6 月起超过美国模型，结构性带动整体 Token 单价从 2026 年开始下滑。
3. 看两阵营交汇点：Coding 是最易落地的场景，原被 Anthropic 独吞；OpenAI、Google、智谱、Kimi 纷纷集中算力提升 Coding 能力，7 月战火燃起。

**关键指标与数据来源**：ARR 月环比增速、OpenRouter Token 用量份额（中/美）、Token 单价；来源为公司披露、OpenRouter。

**判断标准**

- 企业端质量领先 → ARR 环比加速，说明高端定价权在领先模型厂手中；C 端份额由价格与开源决定 → 结构性拉低整体 Token 单价。
- 两阵营的“价格 vs 质量”分化意味着不能用一个平均 Token 单价代表整个市场；要分层看量价。
- 交汇点（Coding）是观察竞争格局是否被打破的窗口：独占被多方集中算力攻击，意味着份额与定价权的边际变化。

**海豚案例**

- Anthropic/大模型《Kimi K3 时刻：中美 AI 产业链叙事要变天？》（2026-07-22）：企业端以 Anthropic ARR 月均环比（25Q4 的 9% → 2026 年 1-2 月 25% → 3-6 月 30% 以上）为质量溢价证据；C 端以 OpenRouter 上中国模型 Token 占比 6 月起超过美国模型、Token 单价 2026 年起下滑为价格敏感证据；Coding 7 月成为多方交汇战场。

**适用场景与注意事项**：适用于判断模型厂的定价权与客户结构。注意 OpenRouter 偏个人与中小团队，不能代表企业市场，不能用它的份额直接推断企业端格局。Agent 付费意愿与算力分配的关联见 3.4.15。

### 3.4.8 训练 vs 推理对存力要求的差异：容量 vs 速度，及“集群资源是否富余”

**方法要点**：反直觉地论证“训练对容量要求更高，但瓶颈在推理”——判断瓶颈不能只看总容量需求，而要看资源切分之后的单实例约束。结论是存力需求应绑定推理调用量，而不是训练集群规模。

**操作步骤 / 拆分口径**

1. 训练阶段
   - 容量要求更高：要存参数的中间状态和计算过程，且仍用 BF16 或更高精度，训练时存参数所需内存是推理的 8-16 倍。
   - 但整个算力集群只训练一个模型（像一个人独享整座仓库），容量相当富余，不构成瓶颈。
   - 传输速度要求不高：训练的计算强度远高于推理，GPU 算力能被用满，很少因等数据而闲置。
2. 推理阶段
   - 集群被切成块，每个模型实例通常只分到几十到数百张卡，容量瓶颈明显。
   - 计算强度低，带宽瓶颈突出；读写量随生成长度激增，速度压力也集中在推理端。
3. 结论：存力瓶颈主要在推理侧，存力需求与 AI 应用渗透、Agent 放量绑定，应跟踪推理调用量，而不是训练集群规模。

**对照表**

| 维度 | 训练 | 推理 |
|---|---|---|
| 总容量需求 | 高：参数中间状态与计算过程，BF16 以上精度，存参数内存为推理的 8-16 倍 | 相对低 |
| 集群资源 | 整个集群投给一个模型，容量富余 | 集群切成小块，每个模型实例只有几十到数百张卡，容量吃紧 |
| 计算强度与速度 | 计算强度高，GPU 被用满，很少等数据，对传输速度要求不高 | 计算强度低，读写量随生成长度激增，带宽瓶颈突出 |
| 瓶颈位置 | 不是存力 | 存力（容量与速度双重压力） |

**关键指标与数据来源**：训练/推理内存倍数（8-16 倍）、每个模型实例可用卡数（几十到数百张）、计算强度、推理调用量。

**判断标准**

- 先比总量，再比“资源切分后”的单实例约束；总量高不等于瓶颈，富余与否取决于集群是否被切分。
- 跟踪变量选“推理调用量”而不是“训练集群规模”；拐点是存储需求的驱动力从训练转向推理时。

**海豚案例**

- 存储《存力接棒算力，HBM为什么“脱颖而出”？》（2026-09-17）：训练容量要求更高（8-16 倍）但集群富余，推理集群被切块后每实例仅几十到数百张卡，存力瓶颈主要在推理侧。
- 存储《（短评）存力真正吃紧的是推理》（2026-10-07）：用“一个人独享整座仓库 vs 仓库被切成小块”的类比讲清楚训练与推理的容量差异；加上读写量随生成长度激增，速度压力同样集中在推理端；结论是存力需求与 AI 应用渗透、Agent 放量绑定，应跟踪推理调用量。

**适用场景与注意事项**：适用于判断 AI 硬件需求在训练与推理之间迁移时，哪些品类受益，以及存储需求驱动力的拐点。各存储品类如何分化见 3.4.9，负载 I/O 画像见 3.4.10。

### 3.4.9 训练→推理迁移对各存储品类需求结构的影响

**方法要点**：从下游 AI 服务器的变化出发，判断存储需求结构：推理时代存储关注点从 HBM 扩散到 DDR、SSD、HDD，而不只是 HBM。

**操作步骤 / 拆分口径**

1. 区分两类投入的性质：
   - 训练是“一次性投入”，成本随性能提升而增加。
   - 推理是商业化落地的刚需，具有规模效应，可以批量摊薄成本。
2. 判断推理端的硬件选择：谷歌 Gemini 性能不差于 GPT，让市场意识到英伟达 GPU 的性能领先在大模型实际应用中并不明显，推理端定制 ASIC 完全可以胜任。
3. 由此推导推理服务器的存储配置：相对更看重 DDR（并发任务）、SSD（快速响应）和 HDD（大容量），而不只是 HBM。
4. 得出两类需求变化：
   - 推理服务器对 DDR、SSD、HDD 的需求相对更多。
   - “内存墙”要求压缩传输距离、提高传输速度。
5. 用该结论解释市场关注点的迁移：2025 年起，市场关注点从 HBM 扩散到传统 DDR 和 NAND。

**品类映射表**

| 存储品类 | 在推理服务器中承担的角色 |
|---|---|
| DDR | 并发任务 |
| SSD | 快速响应 |
| HDD | 大容量 |
| HBM | 缓解内存墙（压缩传输距离、提高传输速度），不再是唯一受益品类 |

**关键指标与数据来源**：训练与推理算力占比、ASIC 出货、AI 服务器单机 DDR/SSD/HDD 配置量。

**判断标准**：训练占比下降、推理占比上升，且推理端出现 ASIC 替代 GPU 的趋势时，非 HBM 品类的相对需求上升；长文本和多模态对容量与速度并重，也推动传统 DDR 需求明显提升。

**海豚案例**

- 存储《存储猛拉，AI存力超级周期到底有多神？》（2026-01-06）：从训练一次性投入 vs 推理规模化刚需出发，推出推理服务器对 DDR、SSD、HDD 的需求相对更多。
- 存储《99%计算闲置？推理时代，存力比算力香！》（2026-01-14）：长文本和多模态对容量与速度的需求并重，2025 年（AI 推理）开始看到传统 DDR 需求明显提升。

**适用场景与注意事项**：适用于判断 AI 硬件链需求结构的变化。训练与推理的占比需要用产业数据持续校准，不能一次判断后固化；“紧缺不只在 HBM”的增量佐证见 3.4.5 变体 B。

### 3.4.10 训练侧 vs 推理侧工作负载的 I/O 画像：突发覆盖写 vs 高并发读

**方法要点**：同一个存储环节（Staging 暂存层），按训练与推理再拆一次负载画像，因为画像不同，对带宽、耐久度、容量的要求就不同，选的介质和受益的产品也不同。

**操作步骤 / 拆分口径**

1. 训练侧：核心是定时存档 Checkpoint 与数据集暂存。
   - 万亿参数模型单次存档 TB 级，每隔几十分钟滚动保存。
   - 虽可异步存档，但集中落盘挤占带宽，存档越久对计算流水线干扰越大。
   - 因此面临“扛覆盖写磨损 + 压缩写入窗口”双重约束。
2. 推理侧：读密集、写极少，典型任务包括：
   - 模型冷启动与弹性伸缩：推理机随早晚高峰频繁调容量，新节点靠本地 SSD 连续读把参数秒级搬进显存，一天可能重载数十次。
   - 多模型/多版本动态常驻：几十 TB 的模型“全家桶”，单卡 288GB 显存差一到两个数量级，只有 4-16TB 直连 SSD 装得下。
3. 把画像映射到要求：训练侧偏写入带宽与耐久度，推理侧偏读带宽与大容量。

**关键指标与数据来源**：Checkpoint 大小与频率（TB 级、几十分钟一次）、重载次数（一天数十次）、单节点 SSD 容量（4-16TB）、显存容量（单卡 288GB）。

**判断标准**：写多读少的负载受益于更耐久的介质，读多写少且需要大容量的负载受益于高容量介质；判断某品类的受益程度，要先判断它面对的是哪种画像。

**海豚案例**

- NAND《从绿叶到鲜花，AI 推理如何为 NAND「逆天改命」？》（2026-09-30）：训练侧 Staging 是突发覆盖写（Checkpoint 滚动存档、挤占带宽），推理侧 Staging 是高并发读（冷启动与弹性伸缩、模型“全家桶”常驻），据此区分对耐久度与容量的不同要求。

**适用场景与注意事项**：适用于拆解 AI 基础设施中训练/推理比重变化对零部件需求的差异影响。画像拆分后的负载占比与介质映射见 3.4.11。

### 3.4.11 按 AI 负载场景 × 介质类型拆分远期需求（Staging / KV Cache / Fast Data Lake；TLC / QLC）

**方法要点**：把远期（2030 年）AI 数据中心 NAND 需求按负载拆成几层，并把每一层映射到具体介质，用来判断不同产品线（TLC vs QLC）与不同厂商的受益程度。

**操作步骤 / 拆分口径**

1. 给出远期总量：闪迪测算 2030 年 AI 数据中心 NAND 需求 1.2ZB，约为 2026 年的 3 倍。
2. 按负载拆成三块并映射介质：

| 负载层 | 占比 | 特征 | 承载介质 |
|---|---|---|---|
| a) Staging 暂存层 | 40% | 贴近 GPU 的极高强度 I/O 缓冲，受覆盖写磨损与高并发约束 | 高性能 TLC（含 pSLC），垄断 |
| b) KV Cache 卸载层 | 35% | 推理时代全新增量，承接 HBM 溢出 | TLC/QLC 梯次承接 |
| c) Fast Data Lake 快速数据湖 | 25% | 远端中央总仓，以读为主 | 几乎全由大容量 QLC 承载 |

3. 按 NAND 类型合计：TLC 占 66%，QLC 占 34%。
4. 指出三类负载的演进方向相反：
   - 数据湖向“更便宜”：QLC 容量放大。
   - Staging 与热路径向“更快更耐用”：TLC 乃至 pSLC，牺牲约 2/3 容量换取约 10 倍耐久。
5. 用拆分结果比较各产品线与各厂商的受益弹性。

**交叉校验（反推，需以厂商口径核实）**：40% + 35% + 25% = 100%。若 Staging 全为 TLC、数据湖全为 QLC，则 KV Cache 层内部大致 TLC 约 26 个百分点、QLC 约 9 个百分点，与“TLC/QLC 梯次承接”的描述一致。

**关键指标与数据来源**：分负载需求占比（40/35/25）、分介质占比（TLC 66%/QLC 34%）、总需求（1.2ZB）；来源为闪迪测算。

**判断标准**：热路径（Staging）的需求看“耐久与速度”，利好高性能 TLC/pSLC；冷端（数据湖）的需求看“单位成本与容量”，利好 QLC；KV Cache 层是新增量，也是估计分歧最大的一层。

**海豚案例**

- NAND《从绿叶到鲜花，AI 推理如何为 NAND「逆天改命」？》（2026-09-30）：采用闪迪 2030 年 AI 数据中心 NAND 需求结构拆分（1.2ZB；Staging 40%、KV Cache 35%、Fast Data Lake 25%；TLC 66%、QLC 34%），并指出 Staging 与数据湖朝相反方向演进。

**适用场景与注意事项**：适用于存储厂商产品结构与受益弹性比较。拆分依赖单一厂商口径，需关注其他机构对 KV Cache 层规模的不同估计；训练侧/推理侧的负载画像依据见 3.4.10。

### 3.4.12 按“计算节点 vs 存储节点”拆分 HDD 在 AI 数据中心的真实需求场景

**方法要点**：不笼统说“AI 拉动 HDD”，而是把 AI 数据中心拆成计算节点与存储节点，分别判断该硬件是否真的会被使用，再聚焦到核心细分品类做供需研究。

**操作步骤 / 拆分口径**

1. a）AI 服务器（计算节点）：HDD 延迟比 SSD 高百倍，机械结构又容易受大功率散热风扇的震动影响，所以几乎不装 HDD。
2. b）AI 数据中心（存储节点）：
   - 训练前要清洗的大量原始视频、图片和文本数据：HDD 的 TCO 只有 SSD 的 1/4 到 1/5，更经济。
   - AI 推理产生的日志、用户交互数据，以及 RAG 需要的底层索引：多存放在大容量 HDD 集群中。
3. 聚焦 NL HDD（近线硬盘，出货占比 8 成以上）作为核心供需研究对象。
4. 用公司指引做需求与供给对照：参考西部数据预期，NL HDD 需求增速 2026、2027 年为 33%、23%，供给增速为 29%、19%。

**关键指标与数据来源**：NL HDD 出货占比、EB 出货量、AI 相关存储节点需求、公司需求预期（如 WDC 指引）。

**判断标准**

- 先判断“硬件在 AI 数据中心的真实位置”：计算节点基本没有，存储节点才有。
- 需求增速高于供给增速即存在缺口：按上述指引，2026、2027 年需求增速分别高于供给增速约 4 个百分点（33% vs 29%，23% vs 19%）；供给侧与缺口的展开见 4.3 与 5.1。

**海豚案例**

- HDD《99%计算闲置？推理时代，存力比算力香！》（2026-01-14）：把 AI 数据中心拆成计算节点（几乎不装 HDD）与存储节点（原始数据清洗、推理日志与 RAG 索引放 HDD），聚焦 NL HDD；参考西部数据预期，NL HDD 需求增速 2026、2027 年为 33%、23%，供给增速为 29%、19%。

**适用场景与注意事项**：适用于判断某种硬件在 AI 数据中心的真实使用位置。数据可参考公司指引（如 WDC），但公司指引有立场，需与第三方数据交叉验证（见 13.1）。

### 3.4.13 训练→推理阶段转换对 CPU 需求的逻辑推演，及 CPU 角色分层

**方法要点**：从训练与推理对 CPU 的依赖差异出发，推演 AI 服务器对 CPU 的需求增加，推动服务器 CPU 涨价、形成 CPU 上行周期；再把 CPU 的角色细分，让新进入者可以选择从增量场景切入。

**操作步骤 / 拆分口径**

1. 训练阶段看重算力，CPU 重要性较弱。
2. 推理阶段看重延迟，CPU 承担资源调度和数据预处理，直接影响吞吐、延迟和效率。
3. 因此 AI 服务器对 CPU 的需求增加，推动服务器 CPU 涨价，形成 CPU 上行周期。
4. 角色分层：通用 CPU、AI 头节点（多核心、海量 PCIe 通道）、智能体（Agent）架构下的 CPU。
5. 新进入者选择增量场景切入，而不是去存量市场正面竞争。

**关键指标与数据来源**：服务器 CPU 价格、CPU:GPU 配比、服务器 CPU 增速指引。

**判断标准**：CPU:GPU 配比上升（管理层指引）是需求逻辑的直接证据；价格上行验证供需转紧；角色分层用于判断一家公司的产品是在抢存量还是吃增量。三类角色的详细口径见 3.4.14。

**海豚案例**

- AMD《CPU“狂飙”》（2026-05-06）：转向推理后，CPU 的调度角色推动服务器 CPU 涨价，管理层把 CPU/GPU 配比提升到 1:1。
- ARM《ARM：“短期波动”难掩锋芒》（2026-05-07）：把 CPU 分为通用 CPU、AI 头节点、智能体 CPU 三类；ARM AGI CPU 瞄准数据中心吞吐和调度的增量需求，不进入 PC 市场与英特尔和 AMD 竞争。

**适用场景与注意事项**：适用于 CPU、服务器链的行业研究。配比与价格是否可持续需要结合供给（产能与扩产节奏，见第 4 章）判断。

### 3.4.14 数据中心 CPU 三分法（传统 / AI 头节点 / Agentic）：按部署形态与需求驱动因子区分

**方法要点**：按部署形态和需求驱动因子把数据中心 CPU 分成三类，目的是认清哪一类是事件带来的纯增量、哪一类是本来就在发生的趋势，并避免后面测算时重复计算。

**操作步骤 / 拆分口径**

| 类别 | 部署形态 | 工作负载与要求 | 需求驱动因子 |
|---|---|---|---|
| a) 传统/通用 CPU | 和 GPU 服务器完全分开，独立部署在传统机架 | 跑 Web、应用服务器、数据库、缓存、存储、消息队列，以串行为主 | 跟着企业 IT 和云的请求量走；新增部分主要来自 agent 访问第三方网站和服务；颗数平稳，核数随产品迭代提升 |
| b) AI 头节点 CPU | 装在 GPU 服务器里，和 GPU 物理绑定，没有独立的头节点机架 | 给 GPU 喂数据、协调通信、管理内存（权重加载、配置 GPU、管理 KV Cache、数据校验）；需要大缓存、高带宽内存和 IO 的高性能单核 | 和加速器数量成正比（GPU 数 × 配比） |
| c) Agentic AI CPU | 独立的 CPU 机架，通过高速网络（Spectrum-X/以太网）和 GPU 机架互连 | 跑 Agent 编排、工具执行、安全沙箱、RAG 检索 | 颗数由并发 agent 数决定，和 GPU 数量无关 |

分类之后的用法：

1. 识别增量性质：c 类是 Muse 带来的纯增量，b 类是本来就在发生的趋势。
2. 避免重复计算：每个需求只归入一类，再各按各的驱动因子测算。

**关键指标与数据来源**：部署形态；驱动因子（请求量 / GPU 数×配比 / 并发 agent 数）。

**判断标准**：分类口径决定后面的测算会不会重复计算；判断某事件是否带来增量，先看它作用于哪一类的驱动因子——只改变并发 agent 数的事件，增量落在 c 类，与 GPU 数量无关。头节点 CPU 增量如何进一步拆成配比、单 CPU 核数、DPU 三个因子，见 12.3。

**海豚案例**

- Muse/CPU《Muse“爆火”…》（2026-09-28）：用三分法拆数据中心 CPU，指出 Muse 带来的纯增量在 Agentic CPU（c），头节点 CPU（b）属于本就在发生的趋势，传统 CPU（a）主要随请求量与 agent 访问第三方服务增长，以此避免测算时重复计算。

**适用场景与注意事项**：适用于 AI 时代的 CPU 需求拆分。三类的边界会随架构演进变化，例如头节点与 Agentic 机架的物理形态，需要持续核对。

### 3.4.15 Chatbot→Agent 演进对算力需求、分配与变现的影响链

**方法要点**：从产品形态的演进（Chatbot→Agent）推导对算力需求、算力分配方向、变现速度乃至组织形态的连锁影响，用于判断 AI 云、模型和应用公司所处的竞争前沿。

**操作步骤 / 拆分口径**

1. 需求端：Agent 对算力和 Token 的需求是 Chatbot 的数倍以上，带动算力需求再次飞速增长，利好算力供应方（云涨价）。
2. 分配端：有限的算力会从 C 端免费 App（成本中心）向更面向办公和 2B 的 Agent 倾斜。
3. 变现端：Agent 用户付费意愿更强，按 Token 付费能立即产生收入，让云和模型公司更早从 AI 获得实际收入和利润。
4. 组织端：推动模型、算力、应用一体化（例如组建 Token Hub 事业群）。
5. 用竞争前沿判断公司位置：从“抢 C 端入口”迭代到“Agent/B 端工作工具”。

**关键指标与数据来源**：Token 消耗增速、云价格、Agent 产品渗透、组织架构变化。

**判断标准**：单个 Agent 的算力与 Token 需求是 Chatbot 的数倍以上，所以 Token 消耗增速应明显快于用户数增速，这是“需求在变形而不只是变多”的信号；云价格上行与算力向 2B 倾斜互相印证；组织上整合模型、算力、应用，是公司对这一变化的响应信号。

**海豚案例**

- 阿里《阿里：电商再沦陷》（2026-03-19）：OpenClaw 在国内传播，竞争前沿从 Chatbot 抢 C 端入口迭代到 Agent；阿里把通义实验室、MaaS、千问、悟空等整合为 ATH 事业群，海豚君认为这有助于技术研发与产品需求对齐。
- 阿里《阿里：电商退位，AI上位》（2026-05-14）：OpenClaw 和 Claude Code 等 Agent 产品快速渗透，竞争前沿从 C 端流量入口转向 B 端工作工具。

**适用场景与注意事项**：适用于 AI 云、模型、应用公司的行业判断。企业端与 C 端的付费分化见 3.4.7，CPU 侧对 Agent 的响应见 3.4.13 与 3.4.14。

**交叉引用**

- 推理时代“AI 基础设施 = XPU + 存储 + 连接”框架，以及 NAND 需求聚焦细分品类、通过产能挤压传导至全行业：详见 1.1。
- 头节点 CPU 增量拆成三个因子（配比 / 单 CPU 核数 / DPU），区分既有趋势与事件带来的纯增量：详见 12.3。

## 3.5 需求弹性、透支与季节波动

> 本节导读：需求测算做完之后，还要检查两类“反向力量”：一是价格或成本上行反过来破坏需求、挤出传统下游；二是时间上的扰动——政策节点前后的提前购买与透支、去年同期的高基数、项目制确认与低价竞争造成的季度波动。用于解读财报季度增速异常、涨价周期里下游消费电子的压力、政策驱动行业的增速拐点。与 3.3（出货 × 单机容量测算中顺带识别涨价挤出）、5.3（价格驱动归因与持续性）、13.2（情景与敏感性）配合；宏观数据（社零等）的基数与季节校正不在此处，见 14.1。

### 3.5.1 上游涨价对传统下游的需求破坏与挤出效应

**方法要点**：评估上游涨价对传统下游的反作用——单机用量虽然仍在上升，但涨价挤压终端厂商成本、影响备货和出货；同时量化 AI 新需求对传统供应的挤出。结果是对传统领域只给中性低增速。

**操作步骤 / 拆分口径**

1. 把“单机用量”和“出货量”分开看：手机和 PC 单机存储需求仍在上升，但存储涨价挤压终端厂商成本（存储占终端 BOM 的成本比例上升），影响备货和出货，市场预估两者出货下滑。
2. 对传统领域只给中性低增速：
   - DRAM 约 +5%。
   - NAND 在手机/PC 两年仅微增。
   - 工业 +5%。
3. 量化 AI 需求对传统供应的挤出：2026 年 AI 服务器 DDR 增量约 66 亿 GB，占 DRAM 整体供应的 15-20%，直接侵蚀 PC 和手机的供应量。
4. 综合判断：传统终端需求 ≈ 单机容量增长 × 受涨价抑制的出货；供给端则被 AI 需求占用，两头夹击传统下游。

**关键指标与数据来源**：手机/PC 出货预期、单机存储容量、存储占终端 BOM 的成本比例、AI 需求占总供应比例。

**判断标准**

- 涨价对需求有破坏：当存储成本占终端 BOM 的比例显著上升，终端厂商会压备货、降出货，即使单机容量在增加，传统领域也只能给低增速。
- 挤出效应有量化口径：AI 服务器 DDR 增量占 DRAM 供应的 15-20%，传统终端是被动让出供应量的一方。
- 常规终端需求按“出货 × 单机容量”测算、并对涨价挤出定性为“缓冲垫”的口径，详见 3.3。

**海豚案例**

- 存储《老黄解锁Rubin，AI存储又添“一把火”》（2026-01-07）：评估涨价对手机和 PC 的影响——单机存储需求仍在上升，但涨价挤压终端成本、影响备货出货，对传统领域只给中性低增速。
- 存储《99%计算闲置？推理时代，存力比算力香！》（2026-01-14）：给出传统领域预期（DRAM 约 +5%、NAND 在手机/PC 两年仅微增、工业 +5%），并量化 2026 年 AI 服务器 DDR 增量约 66 亿 GB，占 DRAM 整体供应 15-20%，直接侵蚀 PC 和手机供应量。

**适用场景与注意事项**：适用于上游涨价周期中评估下游消费电子的压力和需求反馈；反过来也能用于判断消费电子公司的毛利压力。注意“中性低增速”是在涨价压制与单机用量上升两股力量下的折中判断，涨价是否持续决定该判断是否需要下修，价格持续性见 5.3。

### 3.5.2 政策节点前后的需求透支与去年同期高基数识别

**方法要点**：分析季度增速时，先剔除两类非经营因素——政策变化前的提前购买（把需求透支到上一季）、去年同期的高基数——再判断这些影响会持续到哪个季度，从而预判增速拐点。

**操作步骤 / 拆分口径**

1. 识别两类非经营因素：
   - ①政策变化前的提前购买，需求被透支到上一季：购置税恢复前、关税加码前的前置销售。
   - ②去年同期的高基数：国补高峰。
2. 定位关键时点：政策生效时点、去年同期增速、基数结束时点。
3. 判断影响持续到哪个季度（如家电国补高基数持续到 26Q2，下半年恢复正增长）。
4. 据此预判增速拐点：基数结束的季度就是同比增速回正或改善的候选拐点。

**公式（推论）**：同比增速 = 本期 ÷ 去年同期 − 1，去年同期基数被政策抬高，则本期同比被压低；透支则是上一季需求 = 内生需求 + 前置量，下一季需求 = 内生需求 − 前置量。剔除这两项后才是“内生增速”。

**关键指标与数据来源**：政策生效时点、去年同期增速、基数结束时点。

**判断标准**

- 增速下滑若能对应到“透支”或“高基数”，就不应直接解读为经营恶化；反之，基数结束后增速仍无改善，才是真实的需求问题。
- 拐点位置取决于基数结束的时点，例如国补从 24Q3 开始落地，形成 24 年下半年的高基数，持续到 26Q2，则 26 年下半年恢复正增长。
- 透支类事件还会连带库存行为：新车上市前经销商去库存，会进一步放大该季的低点。

**海豚案例**

- 零跑《出海神车…》（2026-03-16）：购置税新政前，1Q26 需求被提前透支到 4Q25；新车上市前经销商去库存。
- 三花《汽零回正…》（2026-05-06）：2025Q1 因美国关税加码前的前置销售和国补高峰，制冷基数高。
- 三花《“天灾人祸”…》（2026-03-31）：国补从 24Q3 开始落地，形成 24 年下半年的高基数，持续到 26Q2；预判下半年恢复正增长。

**适用场景与注意事项**：适用于受政策扰动的消费、汽车、家电行业。宏观高频数据（如社零）的基数与大促校正见 14.1；事件冲击的量化与影响期限见 12.3。

### 3.5.3 储能需求驱动与季度波动解释：需求前置、项目制确认、低价竞争，与 AIDC、新能源配储的长期驱动

**方法要点**：解释储能出货的季度波动时，把短期扰动和长期驱动分开：短期是政策驱动的需求前置和项目制的收入确认波动，长期是 AI 数据中心与新能源配储带来的确定性；同时追踪产能能否支撑需求。

**操作步骤 / 拆分口径**

1. 短期因素（解释单季起伏）：
   - 政策驱动的需求前置：规避关税提升、满足 IRA 本地供应链补贴门槛的抢装。
   - 项目制的收入确认波动：大型 Megapack 的销售、生产、运输、安装周期长。
   - 竞争因素：中国厂商低价竞争。
2. 长期因素（解释中长期确定性）：
   - AI 数据中心需要承接高波动负载、加快并网。
   - 美国新增装机以光伏和风电为主，需要配储调峰。
   - 本土化要求让本土厂商受益。
3. 追踪产能是否能支撑需求：加州、上海、休斯顿工厂，Megapack 3 和 Megablock。
4. 对照订单积压与毛利率：判断低价竞争和关税对盈利的压力。

**关键指标与数据来源**：储能出货量、订单积压、各工厂产能（GWh/年）、IRA 本地化要求、中国厂商价格竞争；来源为财报与电话会纪要。

**判断标准**

- 出货高增若与政策时点（关税、IRA 门槛）重合，先判断为需求前置，而不是长期趋势；随后一季出现环比大幅回落，多半是透支与项目确认节奏所致。
- 长期确定性看两条：AIDC 对储能的需求，以及新能源配储需求；订单积压充足说明长期需求未变，但低价竞争和关税可能让毛利率承压。
- 产能口径要和需求匹配：产能是否足以支撑订单，是长期逻辑能否兑现的约束。

**海豚案例**

- 特斯拉《手撕“烂业绩”剧本》（2026-01-29）：4Q25 出货高增来自关税和 IRA 带来的需求前置，加上 AIDC 和新能源配储的中长期确定性；产能为加州 40GWh、上海 40GWh Megapack 加 6GWh Powerwall，规划休斯顿工厂推动 100GWh/年。
- 特斯拉《造车罕见回血…》（2026-04-23）：1Q26 出货环比 -38%，归因于需求透支、项目确认波动、中国厂商低价竞争；产能口径为 60GWh（加州 40、上海 20、Powerwall 6），目标 66GWh。
- 特斯拉电话会纪要（2026-01-29）：26 年订单积压充足，但低价竞争和关税可能让毛利率承压。

**适用场景与注意事项**：适用于储能和电力设备行业。产能口径在不同季度可能变化：前文是加州 40 + 上海 40（Megapack 合计 80GWh）+ Powerwall 6GWh，后文是 60GWh（加州 40、上海 20、Powerwall 6）、目标 66GWh，上海口径与是否含 Powerwall 前后不一，使用前需核对。项目制确认造成的季度波动，不宜用单季环比外推。
